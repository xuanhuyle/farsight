# ADR-005 — Seeding scheme and deterministic replay addressing
**Status:** Accepted 2026-08-28 (MVP commitment; see Revisit triggers)
**Date:** 2026-08-26
**Deciders:** FarSight founding engineering
**Plan reference:** FARSIGHT_FOUNDATION_PLAN.md §11 (planner and seeding), §12 (determinism rules), decision D9
**Related ADRs:** ADR-000 (the escape-hatch tokens and the `review_signoffs` field this record's checklist item lands in), ADR-002 (the pool never draws, because everything is planned before dispatch), ADR-004 (epistemic parameters are scanned, not sampled, which is what makes a run addressable), ADR-003 (`seed_scope` decides how seeds reach an engine; adapters never sample), ADR-001 (the seed map and the root seed sit inside hashed documents, so seeds are part of run and experiment identity), ADR-006 (Tier A bitwise replay is the property this ADR exists to deliver; owns `ci-worker-order-invariance`), ADR-007 (`runs/seeds_<i>.json` is a mandatory package member), ADR-010 (fault activation draws are ordinary aleatory draws from stream 0 — this record is the authority on the stream registry), ADR-017 (the topology path grammar fixes the sorted draw order stream 0 depends on), ADR-022 (what turns a uniform bit stream into a distribution sample, and whether that is stable)

## Context

The forcing question: given an experiment hash and the number 4242, how do we get the exact bits run #4242 consumed — cheaply, years later, on someone else's machine?

Two failure modes make this hard, and both are ordinary. First, positional derivation: the documented NumPy idiom is `SeedSequence.spawn(n)`, which hands out children in sequence by mutating a counter on the parent. Under that scheme, replaying run 4242 means materializing 4,243 seed sequences, resuming a killed campaign means reconstructing the spawn counter exactly, and any code path that spawns from two places has made the result depend on interleaving order — the precise dependency §12 outlaws. Second, derivation drift: if a package archived in 2026 must call the same library version in 2029 to reproduce, the package is not self-contained and the auditor's laptop is not enough.

Two FarSight-specific facts constrain the shape further. Basilisk has **no global seed** — randomness is configured per module through an `RNGSeed` attribute — so "set the seed" is not an operation that exists; the seed is a map from module name to integer, and the iteration order used to build that map would otherwise leak into hashed results. And FarSight owns all sampling (D11), so the sampler itself consumes randomness (Latin hypercube permutations, stratification) and must not draw from the same stream as the physics, or switching samplers would silently move every physical value.

Concretely, if this is wrong: AT-7 ("run #4242 re-executed standalone from its RunSpec plus seed map is bitwise identical to its in-campaign channels") is both the demo and the debugging story; AT-4 (`kill -9` at 50%, resume, identical hashes) requires that seeds not depend on execution history; and §12's `--workers 1` versus `--workers 8` equality test is satisfiable only if no draw depends on dispatch order.

## Decision

**Root.** One 128-bit root seed per experiment, produced once at plan time from `os.urandom(16)` (or supplied explicitly for replication studies), stored as a decimal string in the `ExperimentDesign` and therefore folded into `experiment_hash` (§7).

**Derivation is direct, never sequential.**

```python
STREAMS = {"aleatory_draws": 0, "engine_module_seeds": 1, "sampler_internal": 2}  # append-only

def stream_rng(root_seed: int, run_index: int, stream_id: int) -> np.random.Generator:
    ss = np.random.SeedSequence(entropy=root_seed, spawn_key=(run_index, stream_id))
    return np.random.Generator(np.random.Philox(ss))   # counter-based; documented stream stability
```

`spawn_key` is constructed directly. It is a pure function of the tuple, so `(experiment_hash, run_index, stream_id)` to bit stream is an O(1) derivation with no predecessors to generate. That single property is what makes replay of run #4242 cheap, resume trivially correct, and worker-count independence automatic. Philox is chosen over `default_rng`'s default because NumPy's stream-compatibility policy commits to named bit generators; the exact current wording is to be re-read and quoted into the module docstring at implementation time.

Stream ids are integers from a frozen, append-only registry — **not** hashes of the stream name, because hashing the name means a rename silently changes every result. Ids 3 through 15 are reserved; an existing id is never renumbered.

**The registry is exactly those three streams.** This record is the authority on it: any other record naming a stream that is not `aleatory_draws`, `engine_module_seeds` or `sampler_internal` is wrong, not ahead. In particular **there is no `fault_activations` stream**, and adding one is not a naming convenience — `stream_id` enters `spawn_key`, so a fourth stream is a different bit stream, different drawn values, different channel bytes and different hashes for every run that touches a fault. See the "Fault randomness is not special" paragraph below for the argument and for the cost the choice imposes.

**Design-scoped keys are a second derivation, not a fourth stream.** ADR-022's frozen `SamplingPlan` carries its own 128-bit `design_seed`, and the Latin-hypercube designs are derived from that root rather than from `root_seed`: `SeedSequence(entropy=design_seed, spawn_key=(0xD5, ...))`, where `0xD5` is the design-scope tag and is deliberately outside the run-index range, and the element after it names which design — `0` the outer stratum assignment, `1` the inner one, the inner form carrying the outer point index after that. These keys are not stream ids and never enter `STREAMS`: they are rooted at a different entropy value, are consumed once by the planner rather than per run, and produce integer stratum assignments rather than physical values. The registry above therefore stays at exactly three, and `stream_rng` is never called with a design-scoped key. Two roots is the price of pinning a stratified design that spans runs: a stratum assignment is a property of the design, and a per-run stream cannot express one.

**Ids 3 through 15 are reserved, and per-entity realization is their intended first tenant.** The registry is append-only and stream ids are addressed directly rather than positionally, which has a property worth naming: appending stream 3 later moves *nothing* in streams 0, 1 or 2, so old campaigns are untouched and only `stream_registry_version` advances for new packages. (Contrast the `fault_activations` proposal above, which would pull existing draws *out of* stream 0 — a destructive change of a different kind.) The anticipated tenant is a FarSight-native engine that must realize per-entity randomness for a population it simulates internally: today such an engine is caught between two rules, since values cannot be pre-drawn per entity into the RunSpec at population scale and `no-naked-rng` forbids it constructing its own generator. When that case arrives it takes a reserved id with a key shape of `(run_index, 3, entity_ordinal)`; it is not designed here, and third-party engines continue to receive integer seeds through `engine_module_seeds` as they do now.

**Run addressing.** `run_index` is assigned by the pure planner as a deterministic lexicographic enumeration of (outer epistemic point index, inner aleatory draw index). The outer loop consumes **no randomness at all** — epistemic parameters are scanned, not sampled (ADR-004: LHS over the epistemic space, interval vertices, model-family enumeration, all deterministic). This is the load-bearing reason a run is addressable as (epistemic point, aleatory draw index): were the outer loop to draw, every outer point's seed would depend on the order the epistemic grid was generated in, and the address would not survive a re-plan.

**Stream usage, fully specified.** `aleatory_draws` (0) is where the planner draws every aleatory value for the run, at plan time, iterating parameters in sorted topology-path order and writing concrete decimal-string values into the RunSpec; a `CorrelationGroup` draws all of its uniforms in one call over sorted member order before the Gaussian copula transform, so membership order cannot shift a draw. `engine_module_seeds` (1) serves adapters declaring `seed_scope == "per_module"` (Basilisk): integers are generated by iterating the adapter's declared module list in **byte-wise sorted order of the ASCII module name** and written into the RunSpec as a sorted list of `(module_name, seed)` pairs. Sorted order is mandatory, not stylistic — it is the only defense against wiring order entering the output hash on an engine with no global seed. `sampler_internal` (2) carries LHS permutations, stratification, and sampler bookkeeping only, isolated so that changing the sampling design does not move the physics draws for a fixed run index.

**Fault randomness is not special.** Stochastic hazard occurrence times, magnitudes, and durations are Beliefs like any other; if aleatory they are drawn from `aleatory_draws` (stream 0) at plan time into the RunSpec's intervention schedule as an ordered list of candidate activation epochs, in the same sorted topology-path order as every other aleatory value. The engine consumes them and never rolls for them; execution echoes what actually fired into `FaultActivationRecord` (ADR-010).

The argument for giving faults their own stream is real and is rejected deliberately. It runs: `sampler_internal` exists precisely so that changing the sampling design does not move the physics draws for a fixed run index, and by the same reasoning adding or removing a fault activation should not move them either. That is true, and it is the cost we are accepting: **editing a fault campaign renumbers nothing but does move every aleatory draw downstream of the edit within each affected run.** We accept it because the alternative is worse in a way that is specific to this product. A fault's magnitude *is* a physical quantity drawn from a Belief; putting it in a separate stream from the pointing jitter it interacts with would mean two parameters of the same physical model are drawn from different bit streams for no reason a reader could reconstruct, and would make the "no second uncertainty system" guarantee (§10) false at the bit level. The stated consequence is the honest one: a campaign whose fault set changed is a **new campaign**, not a variant of the old one, and its `experiment_hash` says so. That is already true for every other design edit, and faults are not exempt.

**Derived values are archived, and replay reads the archive.**

```jsonc
// runs/seeds_4242.json
{ "schema_version": 1, "stream_registry_version": 1,
  "root_seed": "31415926535897932384626433832795028841",
  "experiment_hash": "7d4e...", "run_index": 4242,     // bare 64-hex, no prefix (ADR-001 decision 7)
  "derived_state": { "aleatory_draws": ["0x9f2c...", "..."],   // generate_state words actually used
                     "engine_module_seeds": ["0x1a03...", "..."],
                     "sampler_internal": ["0x77be...", "..."] },
  "engine_module_seeds": [["attitudeNav", 1103515245], ["rwMotorTorque", 2147483629]],
  "aleatory_values": [["flight.laser.pointing_jitter_sigma", "0.16", "urad"]] }
```

Replay consumes the archive; it does **not** re-derive. A `--verify-derivation` flag re-derives and compares, and a mismatch is reported as an environment or library finding, not as a package verification failure. This is the decision that lets a 2026 package replay in 2029 regardless of what NumPy did in between.

**The pool never draws.** No RNG is constructed anywhere in `farsight/experiments/runner.py` or under `farsight/engines/`; `os.urandom` appears in exactly one function, `experiments/seeding.py::new_root_seed`.

## Options considered

### Option 1 — Sequential `SeedSequence.spawn()` — REJECTED
The documented NumPy idiom, obviously correct, and it guarantees non-overlapping children by construction with no reasoning required about key collisions. If campaigns only ever ran start to finish in one process this would be right, and easier to defend to a numerics reviewer. Rejected because children are positional: replaying run 4242 costs 4,243 derivations, resume must reconstruct a mutable counter, and spawning from more than one call site makes results interleaving-dependent. O(1) addressing is not an optimization here — it is what makes resume and replay true rather than aspirational.

### Option 2 — A standardized KDF feeding `SeedSequence`: HKDF-SHA256 (RFC 5869) or SHA-256 counter mode (NIST SP 800-108) — REJECTED
This is not "invent a seeding scheme", and it must not be dismissed as one. The strongest form is: derive a 256-bit value with a published, standardized key-derivation function — HKDF-SHA256 per RFC 5869, or SHA-256 in counter mode per NIST SP 800-108 — over the tuple `(root_seed, run_index, stream_id)`, and feed that value to `np.random.SeedSequence(entropy=...)` and Philox exactly as the chosen option does. Everything the chosen option gets from `SeedSequence` it still gets; only the *addressing* layer changes.

Stated that way it is strictly stronger on three counts, and two of them are load-bearing for this product. It is a named RFC and a NIST publication, so it attracts *less* reviewer scrutiny than the chosen option, which rests on `SeedSequence`'s `spawn_key` mixing — a design we describe in Consequences as "a quality claim resting on `SeedSequence`'s design, not a proof we can produce". It is reimplementable in one shell line in any language, which is exactly the independent-verification property the whole product sells. And, honestly conceded: **it would eliminate the "two sources of truth for every seed" cost this record lists in Consequences**, because a derivation defined by an RFC cannot disagree with an archive of its own output — the `--verify-derivation` flag and the written policy for what a mismatch means would both become unnecessary.

Rejected on a narrower ground than "homebrew is risky", because that ground does not apply. It adds a second derivation layer whose per-run cost buys nothing the archive does not already buy: we archive `generate_state` words regardless, so the auditor's independent check is a byte comparison against the archive either way, and the KDF's shell-one-liner virtue only pays off for a reader who wants to re-derive rather than verify. Against that, `SeedSequence(entropy, spawn_key)` is the idiom a NumPy-literate numerics reviewer expects to see and can audit without reading our code, and one derivation layer is one place for a bug rather than two. The honest summary is that this is close, that the RFC version is defensible, and that the confidence row below reflects that rather than pretending otherwise.

### Option 3 — One global RNG stream consumed in dispatch order — REJECTED
The simplest thing, and what a large fraction of Monte Carlo codes do; no registry, no spawn keys, no per-stream reasoning. Rejected because it makes every drawn value a function of completion order, violating §12 outright and failing the `--workers 1` versus `--workers 8` test on the first run. It is listed because it is what a new developer will propose in week five, and the rejection needs to be on paper.

### Option 4 — Delegate seeding to the engine (Basilisk `setShouldDisperseSeeds` via `MonteCarlo.Controller`) — REJECTED
It exists, it is tested, it is free, and it already does dispersion plus seed dispersal plus a JSON initial-condition archive plus `reRunCases` — a recognizable sketch of what we are building. Rejected because seeds would live in Basilisk's scheme and could not be addressed uniformly across the link chain, SPICE, and GMAT, and because D11 places sampling ownership in FarSight. Its dispersion-*application* classes remain reusable inside the adapter (ADR-003), which keeps the genuinely reusable part.

## Consequences

**Buys us:** O(1) addressing of any run, so AT-7 falls out of the design rather than being engineered; resume correctness for free, since seeds have no dependence on execution history; worker-count independence by construction; an archive that makes replay independent of NumPy's continued existence; and an RNG-free outer loop, so sensitivity attributes cleanly to a named epistemic point rather than to a sampling artifact.

**Costs us:** two sources of truth for every seed — the derivation and the archive — plus a written policy for what a disagreement means and a flag to detect it. Option 2 would have removed that cost, and did not win anyway; the cost is therefore paid knowingly. The stream registry becomes a frozen compatibility surface that can only be appended to. Non-collision of distinct `spawn_key` tuples is a quality claim resting on `SeedSequence`'s design, not a proof we can produce; we test it to 10^5 keys and say so honestly rather than claiming a guarantee. And because faults draw from `aleatory_draws` rather than from a stream of their own, **editing a fault campaign moves the physics draws downstream of the edit in every affected run** — a fault-set change is a new campaign, never a variant of the old one.

**Forecloses:** campaign extension. Because the seed is keyed on `run_index`, adding an epistemic grid point or more inner draws renumbers runs and yields a different `experiment_hash` — so "top up the campaign with 2,000 more samples" is not supported, and a widened study is a new campaign sharing no runs. Recovering that needs `draw_index` in the spawn key, a schema change to a content-addressed document. Second, and deliberately: because all randomness must be planned before dispatch, **adaptive and sequential samplers are structurally excluded** — Bayesian optimization, importance sampling with a fitted proposal, adaptive stratification cannot be expressed at all. That agrees with §2 tripwire #4, but it is a genuine capability given up, and a customer wanting adversarial search will notice.

**The sanctioned shape for search, when it comes, is an external driver above the campaign layer.** Recorded here because this record's foreclosure is what makes the question live, and because the wrong answer — relaxing in-campaign determinism — would cost the product its replay claim. An optimizer, a Pareto explorer or an adversarial searcher sits *outside* FarSight, treats one frozen `ExperimentDesign` as one function evaluation, reads results from the evidence package's schema-validated JSON (ADR-007) or the `--json` contract (ADR-024), and emits the next design as a new draft. Every evaluation stays a fully hashed, replayable campaign; iteration happens in the `exploratory` lane and the frontier points a team actually stands behind are re-frozen attended into evidence-grade campaigns (ADR-001, ADR-004). That requires no schema change and can be built at any time, which is why nothing here reserves anything for it. Two things it must never acquire: preference weights inside a hashed design or criterion, which would put scalarization into the scientific record; and acceptance thresholds that move between iterations, which is automated tolerance-shopping and collides with the plan's zero-count dishonesty tripwire. Only design parameters move across a series; criteria are held fixed.

## Enforcement

- **Hypothesis property suite `test_seed_derivation`** (§14.4), every commit, **first green by week 1**: derivation is collision-free over `(run_index, stream_id)` to 10^5 keys; derivation is enumeration-order independent (forward, reverse, interleaved give identical words); derivation across a process boundary gives identical words; the same `(root, run_index, stream_id)` gives identical `generate_state` output on Windows and Linux. `test_seed_derivation` additionally asserts `design_seed != root_seed` at freeze and that no design-scoped `spawn_key[0]` value is in the run-index range.
- **`no-naked-rng` AST lint**, CI fails on any hit, **first green by week 1**: `numpy.random.*` construction, `random.*`, `secrets.*`, and `os.urandom` are forbidden across `src/farsight/**` except in `farsight/experiments/seeding.py`, with `os.urandom` further restricted to `new_root_seed`. This is the mechanical form of §14's "every draw traces to the master seed" trust precondition.
  `PARTIALLY MECHANIZED: SEED-1` — an AST lint sees syntactic construction sites. It does not see randomness reached through an alias, a `getattr`, a dynamically imported module, or a third-party call that seeds itself internally, and "this function draws no randomness" is not decidable in Python in general. Residue: non-syntactic and third-party draw sites. Two things narrow it rather than wish it away: the lint additionally bans dynamic import and `getattr` on the `numpy` and `random` namespaces anywhere under `src/farsight/`, which converts most of the unsound class into a sound one by constraining the input; and review-checklist item **SEED-1** — *"does any new third-party call in the truth loop consume or seed randomness internally, and if so is its seed set from the run's derived state?"* — covers the rest and lands in `review_signoffs` (ADR-000).
- **RunSpec validator `module_seed_map_sorted`**, **first green by week 2** (with the `execution` schema pack): a RunSpec whose `engine_module_seeds` list is not byte-wise sorted by module name is rejected at construction, so a wiring-order leak cannot reach an engine.
- **Nightly CI job `replay-single-run`** (AT-7), **first green by week 6** — it needs the archived 10k-run campaign fixture, which does not exist until the wk-5/6 campaign machinery lands: pick a pseudo-random run index from that fixture, re-execute from `runspec_<i>.json` plus `seeds_<i>.json` alone with the package as the only input root, and compare channel hashes bitwise.
- **CI job `ci-worker-order-invariance`** (defined in ADR-006; shared with ADR-002, §12), **first green by week 5** — it needs the runner and the package builder: the 100-run experiment at `--workers 1` and `--workers 8` must produce identical evidence root hashes **and** byte-identical `seeds_<i>.json` for every run.
- **`farsight evidence verify`** (defined in ADR-007), **first green by week 4** with the single-run package v0: exits nonzero, naming the run, if any run lacks `seeds_<i>.json`, if `stream_registry_version` is unknown to the reader, or if a seeds file references an `experiment_hash` other than the package's own — and AT-3 requires that flipping one byte of one seed file be caught by exactly this check.
