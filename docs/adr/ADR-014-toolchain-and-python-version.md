**Status:** Accepted 2026-08-28 (MVP commitment; see Revisit triggers)
**Date:** 2026-08-26
**Deciders:** FarSight founding engineering
**Plan reference:** FARSIGHT_FOUNDATION_PLAN.md §3 decision D12, §6, §14, §15, §16, §19
**Related ADRs:** ADR-013 (extras are the mechanism that keeps engines optional), ADR-006 (the environment fingerprint is what a lock hash is *for*; it owns the golden-hash policy this record's fixture rules carry bytes for), ADR-007 (the lock hash ships inside every evidence package; it owns the archived fixture packages), ADR-002 (GMAT lives in a subprocess, which is what makes the interpreter escape hatch cheap), ADR-001 (decimal-string quantities remove the hard part of canonical JSON, which changes the buy-versus-vendor calculus below), ADR-005 (the archived 10k-run campaign fixture the nightly replay test runs against), ADR-011 (package readers are contract-tested against archived fixtures from every prior schema version, forever — the retention obligation this record has to house), ADR-012 (`acquire/` is the code path that restores an external fixture), ADR-019 (the reference container; the interpreter pinned here is the one that image carries), ADR-022 (FarSight implements every sampling transformation itself, which demotes `scipy` from a truth-loop dependency to a test oracle), ADR-025 (the LLM exclusion's lock-file scan runs in this record's `env-guard` job)

## Context

Two forcing questions land in this record, and both are about artifacts that outlive the decision.

**Which interpreter and which lock file**, and it is not a matter of taste here because the environment is part of the claim. Tier A (§12) promises bitwise-equal output hashes given the same container image digest, the same CPU ISA and the same pinned environment; §13 puts an `environment/fingerprint.json` inside every evidence package; D12 puts the `uv.lock` SHA-256 in it. A lock file that cannot be reproduced across the platforms we actually use turns that fingerprint into decoration.

The interpreter is constrained from two directions by verified facts. GMAT R2025a supports Python 3.9 through 3.12, is not pip-installable, and is driven from an application-tree install through its Python API entry point. Basilisk requires >=3.9,<3.15 and ships prebuilt wheels with Windows supported. The intersection ceiling is therefore 3.12, and 3.12 is the highest version inside both. This matters now even though GMAT is post-MVP (§5) — and it is worth saying plainly that this is the uncomfortable part of the pin: the ceiling is set by a component that is behind kill gate K4 and heads §17's scope-cut order.

The platform spread is the other constraint: development happens on Windows, the canonical Tier-A platform is a pinned Linux container (ADR-019), and CI runs both (§17, §19 risk 5). Any locking approach that produces one artifact per platform gives us two or three files that drift, and drift in the pinned environment is indistinguishable from a physics change when a golden hash moves. What breaks concretely: if `uv.lock` does not pin the same resolved versions on Windows and in the container, a Tier-B tolerance miss cannot be attributed. We would be debugging FMA and libm differences (§12) while the actual cause is a SciPy minor version.

**Where the permanently-retained binary fixture corpus lives.** This is the second question and it is the one with a deadline. The ADR set has already committed to an accumulating binary corpus with no home: per-platform golden trees from day one (§12, ADR-006); archived fixture packages (ADR-007); package readers contract-tested against archived fixtures from *every prior schema version*, forever (ADR-011, which also forecloses compressing the record); and an archived 10k-run campaign fixture that the nightly replay test and AT-4 both run against (ADR-005, §18). Nobody chose git, Git LFS, generated-on-demand, or an external store. The choice has to be made in week 1 rather than week 6 because it is the one infrastructure decision in this record that is close to irreversible: a multi-gigabyte blob committed in week 2 comes out only by rewriting history, which invalidates every commit hash anyone has pulled. The rule has to exist *before* the corpus does, which is the only week it is free.

## Decision

**uv plus hatchling, PEP 621 metadata, one committed `uv.lock`.** uv manages the interpreter, resolution, locking, virtual environments and CI invocation; hatchling is the build backend; all project metadata lives in `pyproject.toml` under `[project]`. `uv.lock` is committed, its SHA-256 is recorded in `environment/fingerprint.json` in every evidence package per D12, and — an addition this ADR makes explicit — the lock file itself is copied into `environment/` alongside its hash, so that the hash is checkable by the auditor rather than merely present.

**Python 3.12, pinned as `requires-python = "==3.12.*"`.** The constraint chain is: GMAT R2025a supports 3.9-3.12; Basilisk requires >=3.9,<3.15; the intersection is 3.9-3.12; we take the ceiling.

**The escape hatch, deliberately unused.** Because GMAT only ever runs inside an isolated subprocess (ADR-002, forced by its per-process singleton engine and lack of thread safety), splitting the environment later — core on a newer interpreter, GMAT workers on 3.12 — is architecturally trivial: the worker boundary is already a serialized `RunSpec` in and a result record out, with no live objects crossing. We are not doing it now, and the reason is evidentiary rather than technical: two interpreters means two lock files and two environment fingerprints inside one evidence package, and every fingerprint we add is a claim an auditor has to check and we have to keep true.

```toml
[project]
name = "farsight"
requires-python = "==3.12.*"
dependencies = [
  "pydantic>=2,<3",      # schemas: the only typed vocabulary (ADR-001, §7)
  "numpy>=1.26,<3",      # channels, Philox/SeedSequence (ADR-005)
  "scipy>=1.11,<2",      # test oracle for inverse-CDF accuracy (ADR-022); retained in core only while ADR-007's `verify` dependency set names it
  "astropy>=6,<8",       # BSD-3; boundary unit typing only, never inner loops (ADR-008)
  "typer>=0.12,<1",      # the CLI is the whole UI (§16: no web UI)
  # RFC 8785 (JCS) canonical JSON - concrete package UNVERIFIED, see below
]

[project.optional-dependencies]
spice    = ["spiceypy>=6,<7"]   # MIT wrapper, bundled CSPICE; KernelPool context manager.
                                # An EXTRA, not a core dependency: the auditor's zero-extras
                                # install must not pull a compiled CSPICE (ADR-007, ADR-013).
basilisk = ["bsk"]       # ISC; version floor >= the post-construction RNGSeed fix - UNVERIFIED, set in the week-1 spike (§20.4)
gmat     = []            # deliberately empty: GMAT is a user-installed tree, not a dependency
analysis = ["pandas", "matplotlib", "jupyterlab"]   # quarantined by ADR-013
dev      = ["pytest", "pytest-socket", "hypothesis", "import-linter", "ruff", "mypy", "pytest-cov"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

`spiceypy` as an extra is a departure from §6's extras list and is requested as a plan amendment in the References below; it is not a silent divergence. `pytest-socket` is in `dev` because it is the mechanism ADR-012's `test-no-sockets` job names, and a job that names no mechanism is an intention.

Everything else the MVP needs is standard library and therefore not in the trust surface at all: `sqlite3` for the run ledger, alias registry and hash-chained audit log (D10, §16); `hashlib` for SHA-256; `concurrent.futures` for the spawn-context process pool (§11); `json`, `decimal`, `pathlib`.

On canonical JSON: the requirement is an RFC 8785 (JCS) profile — UTF-8, sorted keys, no insignificant whitespace. The concrete third-party package is **UNVERIFIED — confirm at implementation time**. Note that ADR-001's decimal-string rule (D5: `{"magnitude": "0.22", "unit": "m"}`, never JSON floats in hashed documents) removes JCS's hardest requirement, ES6 number serialization, from our path entirely. A vendored canonicalizer of a few hundred lines is therefore a legitimate outcome of that evaluation, and given that hashing is the foundation of every product claim, owning and property-testing it (§14.4, week 1) may be preferable to depending on it.

On GMAT: it is deliberately **not** a pip dependency. The adapter shells out to a user-installed tree, which is recorded in the registry as an `EngineBuild` with install path, reported version string, and a content hash over a declared file set (the Python API entry point at minimum; exact file set and the entry point's filename **UNVERIFIED — fix during the week-1 GMAT subprocess spike**). Beyond matching GMAT's actual distribution model, this sidesteps the redistribution audit of the third-party components bundled in GMAT's binary distribution, whose inventory §15 records as unverified.

**The binary fixture corpus: three retention classes, sorted by whether the bytes are reproducible.**

1. **In git, always — text and only text.** Golden *hash* manifests, JSON Schema exports, canonical-JSON fixtures, `EXPECTED-CHANGE` notes, and `fixtures/manifest.json` itself. A golden hash is sixty-four characters; the array it was computed over is needed to *diagnose* a change, never to *detect* one, and detection is what runs on every commit. A hard cap backs this: **no file over 1 MiB and no `.npy` at any size ever enters git history**, enforced from the first commit by a pre-commit hook and by CI, because the rule is worthless the day after it is first broken.

2. **In an external content-addressed fixture store, retained forever — bytes we cannot regenerate.** Archived evidence packages from every prior schema version (ADR-011 contract-tests readers against them forever, and current code cannot reproduce a prior-schema package — that is the entire point of the test); archived external goldens under §14 item 5, whose admissibility depends on *not* having come from our code (Horizons responses, hash-pinned cited datasets); and the one reference campaign fixture that AT-4 and the nightly replay test run against. Objects are addressed by SHA-256. `fixtures/manifest.json` is committed to git and carries, per entry, a logical name, the SHA-256, the byte size, a retention class, and a declared origin. Retrieval is `farsight fetch` — the `acquire/` path, which already records URL and hash (ADR-012, §16 item 1). The store's concrete provider and location are **UNVERIFIED — chosen at implementation time**, with the requirement that it be mirrorable onto an air-gapped build host, because the product's posture is offline-first and the test corpus should not be the one thing that needs the internet.

3. **Generated on demand, stored as a cache and never as a record.** Per-platform golden channel trees at the *current* schema version, and any bulk campaign output that is bitwise reproducible in the pinned container by construction. Tier A's whole claim (§12, ADR-019) is that these can be recreated; storing them is therefore a convenience, and a cache miss costs time and never correctness. CI may cache them in the same store keyed by content hash.

The restore step is a network operation and it happens *before* the socket-disabled test leg (`test-no-sockets`, ADR-012), not inside it. Nothing in the truth loop — runner or verifier — ever reaches the store; the CI harness does, once, at setup.

**Deliberately not yet, with reasons.** pandas outside `analysis/`: a DataFrame makes column dtype and ordering implicit in a system where §12 forbids any hashed value depending on iteration order; truth-loop arrays are named `.npy` files. Pint: unit objects cost 20-100x per scalar op (§8), fatal at 10k-run scale, and astropy already covers the boundary. h5py: HDF5 files are not byte-stable across writer versions, so hashing the file would stop being hashing the numbers. pyarrow/Parquet: reconsidered at scale phase, and leaving it out keeps it off the MVP trust surface (§7). dask/ray/celery: `ProcessPoolExecutor` is deliberately boring and the runner interface is the seam for a distributed backend (§11); a scheduler that reorders completion is the wrong thing to add to a system whose central regression test is that `--workers 1` and `--workers 8` produce identical root hashes. PostgreSQL drivers: D10, packages are files, there is no DB roadmap line. Docker SDK: §16 keeps a reference Dockerfile and records image digests (ADR-019); we do not drive Docker from Python. Git LFS: rejected below with reasons. Any web framework: §2 tripwire 5, no frontend dependency for eight weeks. Any LLM SDK: ADR-025, structural absence enforced by an import-linter contract and a lock-file scan. tudatpy: BSD-3 and legally fine, but conda-only distribution would force a second package manager into the lock story, which is a change to the reproducibility architecture rather than an added dependency. F Prime: Apache 2.0 with the Caltech notice interplay still in legal review (§15), and §2 tripwire 2 forbids a third engine before the second earns its keep. scikit-optimize, BoTorch and GPy are already an automatic revert under §2 tripwire 4.

## Options considered

### Option 1 — Poetry — REJECTED
Mature, widely known, a deterministic lock with recorded hashes, and real team familiarity, which is a genuine schedule saving in week 1. Rejected on interpreter management: Poetry resolves against an interpreter it does not install, so we would add pyenv or equivalent on Linux plus a separate Windows story, and "which Python 3.12" would remain an ambient property of each machine — precisely the property that Tier A needs to be pinned. Its historical non-PEP-621 metadata dialect also adds a translation step for a `pyproject.toml` that gets quoted into evidence.

### Option 2 — pip-tools (`requirements.in` compiled to hash-pinned `requirements.txt`) — REJECTED
The most auditable output of the three: a flat, hash-pinned requirements file that an auditor can read with no new tooling, installable by pip alone. That merit is real and partly survives our choice, because we still publish a wheel with standard metadata and the auditor path stays plain pip. Rejected because pip-tools compiles per platform: Windows dev plus Linux CI plus the pinned container means two or three files that drift silently, and it manages neither interpreters nor an extras structure matching ADR-013's extras.

### Option 3 — conda/mamba — REJECTED
The only manager that could host tudatpy today and the one with the most uniform story for compiled scientific stacks. Rejected because conda environments are materially harder to pin to a byte-identical solve, which is the one property we are optimizing for, and tudatpy is out of MVP scope anyway.

### Option 4 — uv plus hatchling — CHOSEN
uv installs and pins the interpreter itself, so "Python 3.12" becomes an artifact rather than an ambient fact; it produces a single cross-platform lock with hashes covering Windows and Linux from one file; and it is fast enough that a cold-cache CI install does not become the slowest job, which matters because ADR-013's `auditor-install` job builds a clean environment on every push. hatchling is a plain PEP 517 backend with no opinions we have to work around. The honest cost is maturity risk: uv is younger than the alternatives, and an evidence package that records a lock hash is worthless if a future uv cannot read that lock — which is why the lock file itself ships inside the package next to its hash, so the artifact remains self-describing even if the tool moves.

### Python version — 3.11 versus 3.12 versus 3.13+ — 3.12 CHOSEN
3.13 or newer is outside GMAT's ceiling and would force the two-interpreter split immediately, paying the two-fingerprint cost in week 1 for a benefit we have not identified. 3.11 has a real argument — broader wheel availability across the scientific stack — but that argument is mechanically testable rather than debatable: if any required dependency lacks a 3.12 wheel, `uv lock` fails in week 1 and this ADR is revisited on the spot. 3.12 is the ceiling of the intersection, which maximizes the time before the floor of some future dependency rises above us. What we are accepting, and it is the reason this sub-decision carries the lowest confidence in the record: the ceiling is inherited from a component that is post-MVP, sits behind K4, and is item 1 on the scope-cut list, and the pin costs tudatpy outright in the meantime.

### Fixture corpus — commit the binaries to git — REJECTED
One clone, one integrity story, no second system, no provider relationship, and the corpus is covered by the same hashes as the code — for an offline-first product whose auditor gets "only the package, the CLI and the README", that is a genuinely attractive property, and it is the default that costs nothing to start. Rejected because the corpus is unbounded, permanent, and uncompressible by our own decisions: ADR-011 retains a package per schema version forever and forecloses compressing the record, ADR-006 keeps per-platform golden trees, ADR-005's nightly replay wants a 10k-run campaign fixture. The order of magnitude — from ADR-004's 24-outer-by-400-inner sampling plan, a per-pass sample count, and a dozen channels — is gigabytes in of order 10^5 files per campaign (**UNVERIFIED** until ADR-011's week-4 package-size measurement). Git keeps every version of every blob forever, so the mistake is not "the repo is large" but "the repo cannot be made small again without a history rewrite that invalidates every commit hash anyone holds." That is the irreversibility, and it lands in week 2. Hosting providers additionally impose per-file and per-repository limits (**UNVERIFIED** — confirm against the provider chosen at implementation time).

### Fixture corpus — Git LFS — REJECTED
This is the standard answer and it deserves a real hearing. It keeps a single `git clone` workflow, pointer files are text so history stays small, LFS objects are content-addressed by SHA-256 — which is exactly our identity model — and every major host supports it with no bespoke tooling from us. Rejected on three grounds, in increasing order of severity. (i) It puts `git lfs` on the critical path of the auditor's machine and of any air-gapped build host, which sits badly with a product whose §16 posture is offline-first. (ii) Its characteristic failure is silent and looks exactly like the failure we exist to detect: a clone without LFS configured, or a mirror that did not carry the objects, produces a small text pointer file where a `.npy` is expected, so a test suite reads *wrong data from a clean checkout* — the corpus equivalent of verification passing on mutated evidence, which §14 item 9 calls theater. (iii) It does not actually solve permanence: pointers remain in history whatever is pruned server-side, so the irreversibility is only relocated, and storage becomes a provider quota and bandwidth relationship, which makes the ability to run our own nightly tests a billing question.

### Fixture corpus — generate everything on demand, store nothing — REJECTED
Zero storage, no second system, and it is justified by our own thesis: Tier A asserts bitwise reproducibility in the pinned container (§12, ADR-019), so a stored golden tree is a cache of something we claim we can recreate. It also sidesteps the irreversibility problem entirely. Rejected on one decisive case and one practical one. Decisive: it cannot hold a package produced by a *prior* schema version, and ADR-011 requires readers contract-tested against exactly those, forever — current code regenerating them would defeat the test. The same logic voids §14 item 5's external goldens, which are admissible *because* they did not come from our code; regenerating a Horizons response is a category error. Practical: making the nightly replay check depend on first running a multi-hour campaign turns a fast check into one that gets disabled the first busy week.

### Fixture corpus — tiered: text in git, irreproducible bytes in an external content-addressed store, reproducible bulk generated on demand — CHOSEN
It puts each artifact where its own reproducibility says it belongs, keeps the clone small and the history clean, and — the property that actually decides it — it makes the irreversible mistake impossible to commit, because the guard exists from the first commit rather than from the first complaint. The cost is a second system and an unchosen provider, both stated below.

## Consequences

**Buys us:** one lock file that pins the interpreter and every dependency across both platforms; a lock hash that makes the evidence package's environment claim checkable; an interpreter that is legal for both engines, so the GMAT adapter needs no environment work when it lands; a small, boring dependency set whose licenses (MIT, BSD-3, ISC, Apache-2.0) are all cleared in §15; a base install with no compiled engine in it, which is the property AT-9's auditor tests in week 8; and a repository that can still be cloned in week 6.

**Costs us:** we are on the newest of the three toolchains, and a uv regression is a schedule risk with no in-house fallback beyond exporting requirements. We are one minor version below the current Python frontier and will stay there while GMAT's ceiling holds, so any 3.13+ performance or typing improvement is unavailable. Pinning `==3.12.*` also means a contributor with only 3.11 or 3.13 installed cannot run the suite until uv fetches the right interpreter. And the fixture corpus is now a second system with its own provider, its own restore step, its own failure mode (a store outage stops the nightly replay test, though never the truth loop), and an unbounded retention obligation that only grows: every schema version we ship adds an archived package we must keep forever.

**Forecloses:** using tudatpy at all without either adopting conda or waiting for a wheel — a real loss, because TudatPy is BSD-3 and would otherwise be the cheapest third propagator. It forecloses moving core to a newer interpreter without either dropping GMAT support or accepting two lock files and two environment fingerprints in every evidence package. A single lock across core plus all extras means a future adapter with an incompatible pin is not a local inconvenience but the event that forces ADR-013's workspace split. And the 1 MiB / no-`.npy` rule forecloses the convenience of a self-contained clone: from week 1 onward, a fresh checkout cannot run the golden or replay suites without a network fetch or a pre-populated mirror, and a contributor on a train is blocked from exactly the tests that matter most.

## Enforcement

- **CI job `env-guard`** (first green by **week 1**; every push, on Windows and Linux runners and inside the pinned container). It runs `uv lock --check` (fails if the committed lock is stale with respect to `pyproject.toml`) and `uv sync --locked` (fails rather than silently re-resolving); exact flag spellings to be confirmed against the uv version pinned at implementation time. It then runs `tests/unit/test_environment.py`, which asserts `sys.version_info[:2] == (3, 12)`, asserts that the fingerprint writer emits a `uv_lock_sha256` field, and asserts that the emitted value equals the SHA-256 of the repository's `uv.lock` at build time. Two further legs run inside this job: `ci-base-install-dependency-lint` (defined in ADR-011) and the LLM lock scan `tests/unit/test_no_llm_dependency.py` (defined in ADR-025).
- **`tests/unit/test_dependency_allowlist.py`** (first green by **week 1**) is the single source of truth for the dependency allowlist: the set of top-level distribution names in `uv.lock` outside the `analysis` and `dev` extras must equal a literal list checked into the test, and analytics and error-reporting SDKs sit on a permanent denylist inside it. ADR-011 and ADR-012 reference this module by name rather than re-specifying the check; a Markdown table is a fragile machine input and there is exactly one list.
- **CI job `ci-repo-size-guard`** (first green by **week 1**, and this is the item whose value is entirely in its start date): fails if any file added in the commit range exceeds **1 MiB**, if any path matching `*.npy` is added under version control anywhere outside a declared throwaway directory, or if the working tree's total binary bytes exceed a declared budget. It is mirrored by a `pre-commit` hook so that the common case fails before the object is in anyone's local history, where a CI failure can no longer help.
- **`tests/unit/test_fixture_manifest.py`** (first green by **week 2**): every entry in `fixtures/manifest.json` carries a SHA-256, a byte size, a retention class in `{retained, generated}` and a declared origin; every `retained` entry restored by CI hashes to its recorded SHA-256; no test in the suite references a fixture path that is absent from the manifest. A fixture that appears in the tree without a manifest row fails the build, which is how the corpus stays enumerable rather than accreting.
- **PARTIALLY MECHANIZED:** the manifest's `origin` field is a declaration. A lint can check that it is present and drawn from the enumerated set; it cannot check that it is true, and "these bytes came from Horizons and not from us" is precisely the claim §14 item 5 rests on. ADR-006 owns the golden-provenance attestation for golden *numbers*; this record guarantees only that the *bytes* are addressed, retained and enumerated. The residue is review-checklist item **FIXTURE-1** ("is this retained fixture's declared origin its actual origin, and are these bytes genuinely irreproducible rather than something the pinned container could regenerate?"), whose sign-off lands in the `review_signoffs` list on the frozen `EvidencePackage` (ADR-000).
