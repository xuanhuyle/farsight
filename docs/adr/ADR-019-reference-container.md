# ADR-019 — The reference container and Tier-A environment identity
**Status:** Accepted 2026-08-28 (MVP commitment; see Revisit triggers)
**Date:** 2026-08-26
**Deciders:** FarSight founding engineering
**Plan reference:** FARSIGHT_FOUNDATION_PLAN.md §12 (Tier A), §8 (environment pins in every worker), §13 (`environment/fingerprint.json`), §16 (reference Dockerfile plus digest recording), §17 (weeks 1-2: repo plus CI plus pinned container), §19 risk 5, §21 gate K3 and the standing reproducibility kill; decision D13
**Related ADRs:** ADR-000 (the escape-hatch tokens this record's Enforcement uses), ADR-002 (owns `_THREAD_ENV`; this record owns `_ISA_ENV`, applied by the same function before the numeric stack imports), ADR-006 (owns the tier definitions and `ci-tier-a-bitwise`; this record resolves what its Tier-A predicate actually is), ADR-007 (the image is deliberately not package content, which is why step 3 of the audit path carries an install caveat), ADR-008 (the numerics rationale for pinning threads, and the tolerance conventions Tier B falls back to), ADR-011 (the `.npy` channel bytes that "bitwise" is measured over), ADR-012 (deferred container tooling to a reference Dockerfile plus digest recording, and supplies the isolated-network-namespace leg), ADR-013 (the zero-extras auditor install is a different artifact from this image and must not be confused with it), ADR-014 (uv manages the interpreter, `uv.lock` is the resolved set this image materializes), ADR-024 (the environment-refusal exit code a below-baseline machine receives)

## Context

The pinned container is a weeks 1-2 deliverable and **K3, the plan's only hard gate, is defined entirely in terms of it**: the full pipeline rerun in the same container must yield a bitwise-identical evidence root hash, twice, including once after a reboot, or all feature work stops. Three records point at this container and none of them decides what it is. ADR-006 makes the container digest part of the Tier-A predicate and says explicitly that the container is ADR-019's decision. ADR-012 defers "container tooling beyond a reference Dockerfile plus digest recording" and names this record as the owner of what that Dockerfile is. ADR-014 pins the interpreter, the lock file and the dependency set and never mentions an image at all.

Three things have to be settled and each of them can silently falsify a Tier-A claim.

**Base image pinning.** A tag is mutable. If the Dockerfile says `FROM python:3.12-slim`, two CI runs a week apart legitimately execute different images while both stamp the same environment, and K3's "twice, including once after reboot" can straddle a tag move. Tier A becomes non-reproducible by construction, and the failure looks like a FarSight bug.

**glibc and libm provenance.** ADR-006 names libm differences across operating systems as one of the things that break bitwise equality. A version string is not provenance: two `glibc 2.36` builds with different patch levels or different compiler flags can produce different `sin` in the last bit, and nothing in the current fingerprint would show it.

**BLAS vendor and CPU dispatch, which is the sharp one.** ADR-008 pins `OPENBLAS_NUM_THREADS=1` and its siblings, and thread count is not the variable that bites here. OpenBLAS selects kernels by CPUID at run time, and NumPy runs its own runtime SIMD dispatcher on top. The same wheel, the same lock file and the same thread pins produce **different machine code** on an AVX2 runner and an AVX-512 runner, which means different reduction orders inside a dot product, which means different bits. ADR-006 absorbs this by putting "same CPU ISA feature set" into the Tier-A predicate, and that sentence silently converts into an unbudgeted operational requirement that the CI runner fleet be silicon-homogeneous - and into an unenforceable requirement on customers, who build their own packages on their own machines (ADR-012). A Tier-A check that goes red because two runners have different silicon is indistinguishable from a FarSight bug, is exactly the "unpassable for undiagnosable reasons" failure ADR-006 names, and feeds the standing reproducibility kill: two calendar weeks without Tier-A bitwise replay and the thesis dies.

Two further questions have no owner. How does an auditor obtain the image for a Tier-A replay in a product whose posture is offline-first and whose deployment model includes air-gapped sites? And who owns the re-golding cycle when a base-image CVE update lands - ADR-006 names that consequence in its Forecloses and assigns no policy to it.

## Decision

**1. One reference image, built from `container/`, base pinned by digest.**

```
container/
  Dockerfile          # FROM debian:bookworm-slim@sha256:<digest recorded in digests.json>
  packages.txt        # every apt package with an exact =version pin, one per line
  build.sh            # deterministic build entrypoint used by CI and by hand
  digests.json        # numeric_environment_hash + accepted_image_digests + build manifest hash
```

The base is a minimal Debian, referenced **only** by digest; a `FROM` line without an `@sha256:` prefix fails the build job. Every apt package is version-pinned in `packages.txt`. The interpreter is **not** taken from the base image: uv installs and pins it exactly as ADR-014 decided, so "Python 3.12" is one artifact identity shared by the Windows development machine and the container rather than an ambient property of each. The image materializes `uv sync --locked` with the `spice`, `basilisk` and `dev` extras, so every Tier-A claim the MVP makes is executable inside one image. Concrete digests are never written into this record; they live in `container/digests.json`, which is text and therefore in git under ADR-014's rules.

This image is the **evidence-producing** environment. It is not, and must never be confused with, the zero-extras auditor install of ADR-013: that is a `pip install farsight` with no engine extras, and it exists to prove `verify` needs no engines. Different artifact, different purpose, different property.

**2. The Tier-A predicate is `numeric_environment_hash`, not the container image digest.** This is the load-bearing decision in the record and it is a deliberate refinement of ADR-006, whose 0.70 confidence row already names "a re-definition of Tier A against a normalized numeric environment (ADR-019) rather than raw silicon" as its own revisit trigger.

```json
{"schema_version": "numeric_environment/1",
 "isa_baseline": "x86-64-v3",
 "isa_enabled_features": ["AVX", "AVX2", "FMA3", "..."],
 "interpreter": {"version": "3.12.x", "binary_sha256": "<64-hex>"},
 "uv_lock_sha256": "<64-hex>",
 "mapped_libraries": [{"soname": "libc.so.6", "path": "/lib/...", "sha256": "<64-hex>",
                       "size_bytes": 0}],
 "blas": {"library_path": "...", "library_sha256": "<64-hex>", "coretype": "..."},
 "thread_env": {"OMP_NUM_THREADS": "1"},
 "engine_build_ids": ["<64-hex>"]}
```

`numeric_environment_hash = sha256(JCS(...))` over that document. Every field is measured **from inside the running worker, after the numeric stack has imported** - not declared. `mapped_libraries` hashes the actual shared-object files the process has mapped, which is what makes "glibc and libm provenance" a fact rather than a version string: two builds of the same glibc version produce different SHA-256 values and therefore a different predicate. All numbers in the document are exact-range integers; every other quantity is a string (ADR-001). Every digest-valued field here — `binary_sha256`, `uv_lock_sha256`, each `mapped_libraries[].sha256`, `blas.library_sha256`, each `engine_build_ids` entry — is bare 64 lowercase hex with no `sha256:` prefix, because this is a hashed document and ADR-001 decision 7 admits the prefix only in human-facing output and prose.

`environment/fingerprint.json` (§13) then carries two things with different force:

- `numeric_environment_hash` - **the predicate**. `farsight evidence replay --tier A` refuses, naming the differing field, when it does not match.
- `container_image_digest`, `cpu_model_string`, `os_release`, `kernel` - **provenance only**. A mismatch is reported and does not refuse.

There is a concrete reason the image digest cannot be the predicate even if we wanted it to be: **a container cannot reliably read its own image digest from inside.** The digest is computed after the build, by the builder, and whatever the runtime injects is a value the operator asserted. A predicate we cannot measure is a predicate we cannot enforce, so the digest is recorded as `source: reported` and treated as untrusted provenance, while everything the predicate rests on is measured in-process.

**3. Runtime CPU dispatch is pinned to a declared baseline, and the fleet is not.**

```python
# farsight/engines/worker.py - applied together with ADR-002's _THREAD_ENV,
# before the first numpy import. ADR-002 owns _THREAD_ENV; this record owns _ISA_ENV.
TIER_A_ISA_BASELINE = "x86-64-v3"          # AVX2 + FMA + BMI2, the psABI level
_ISA_ENV = {
    "OPENBLAS_CORETYPE": "<baseline coretype>",           # UNVERIFIED - confirm the variable
    "NPY_DISABLE_CPU_FEATURES": "<features above baseline>",  # name and accepted values against
}                                                          # the versions uv.lock resolves
```

Both variable names and their accepted value vocabularies are **UNVERIFIED - confirm at implementation time** against the OpenBLAS build inside the NumPy wheel and the NumPy version `uv.lock` resolves. The decision is the mechanism, not the spelling: suppress dispatch above a declared baseline rather than require identical silicon.

The consequences of that choice, stated plainly:

- Any machine at or above `x86-64-v3` normalizes to the same enabled feature set and therefore to the same `numeric_environment_hash`. A heterogeneous fleet of AVX2 and AVX-512 runners is **fine**, which is what removes the unbudgeted silicon-homogeneity requirement.
- A machine **below** the baseline cannot be normalized upward. The worker detects this at start, before producing any output, and exits with the environment-refusal code (ADR-024) naming `isa_baseline`. It never emits a Tier-A-labelled artifact. This is the whole point: an environment that cannot support the claim produces a named refusal at job start rather than a mismatched hash three hours later that nobody can attribute.
- `aarch64`, including Apple Silicon development machines, is **outside Tier A for the MVP**. It has a different baseline, a different BLAS kernel set and would need its own golden tree. Runs there are Tier B, and we say so rather than discovering it in week 6.

The measured feature set is read back after import and folded into `isa_enabled_features`, so a pin that silently failed to take effect changes the hash instead of hiding.

**4. The auditor obtains the image, or rebuilds an equivalent one, and either way Tier A is decidable.** FarSight does not pull container images - ADR-014 rules out driving Docker from Python, and ADR-012 keeps `acquire/` to HTTP fetches of content-addressed data. Three routes, and the predicate is what makes all three work:

- **Registry pull by digest**, with the operator's own container runtime. Normal case for us and for connected customers.
- **A `docker save` tarball**, whose SHA-256 is recorded as a `DataArtifact` and which the customer copies into an air-gapped site. This is the route we actually support for the deployment we optimize for.
- **Rebuild from `container/Dockerfile` plus `packages.txt` plus `uv.lock`**, all three of which ship inside `environment/` in every evidence package. A rebuild does **not** reproduce the image digest - apt repository state and layer metadata move - and under an image-digest predicate the rebuild would be worthless. Under `numeric_environment_hash` it is not: if the rebuild resolves the same interpreter, the same locked set and the same mapped libraries, the predicate matches and Tier A holds. That is the second reason the predicate was moved, and it is the one an auditor cares about.

**5. Re-golding on a base-image change has a named owner and a mechanical decision rule.** `container/` carries a CODEOWNERS entry naming one developer as the container owner. `ci-container-refresh` runs monthly and on any security advisory affecting a pinned package. It rebuilds and compares:

- `numeric_environment_hash` **unchanged** - the new image digest is appended to `accepted_image_digests` in `digests.json` and nothing is re-golded. Most CVE updates land here, because most patched packages are not mapped by the numeric stack.
- `numeric_environment_hash` **changed** - the job fails, names the changed field, and the container owner performs the re-golding under ADR-006's `EXPECTED-CHANGE` discipline with a second-developer review. Goldens move deliberately, once, with a reason.

The honest cost is stated rather than hidden: when a patched package *is* in the mapped set and a campaign is mid-flight, we accept the un-patched library inside the Tier-A image until the campaign closes rather than move the numeric environment underneath a running claim. The exposure is bounded by the container running no network service and consuming only content-addressed local inputs (ADR-012), and Tier-A runs execute with the network namespace disabled. It is bounded, not zero, and a customer security team will ask about it.

## Options considered

### Option 1 — Tag-pinned upstream image (`FROM python:3.12-slim`) — REJECTED
Steelmanned: it is what essentially every Python project does, it inherits upstream security patches for free with no refresh job and no owner, it is one line, and the actual digest still lands in the fingerprint at run time, so you can always say *what you ran*. Rejected because Tier A is a predicate evaluated before and after a run, not a log line. A mutable tag lets two runs a week apart execute different images while claiming one environment, and K3 explicitly spans a reboot, so a tag move can sit between the two halves of the gate. The recorded-digest defence also collapses for replay: an auditor pulling the same tag six months later gets a different image and has no way to obtain the original.

### Option 2 — Digest-pinned upstream `python:3.12-slim-bookworm` — REJECTED, and it is close
Steelmanned properly, this is the smallest correct thing: fewest moving parts, a well-tested Docker Official Image, an interpreter built by people who do that for a living, and it removes uv's interpreter management from the Tier-A story entirely. Rejected on one specific ground rather than on general preference: the interpreter would then come from the image and would exist only in the container, while ADR-014 chose uv precisely so that "Python 3.12" is one artifact identity spanning the Windows development machine and the container. Two interpreter provenances means a Tier-B discrepancy between Windows and the container has one more unattributable cause, which is the exact failure ADR-014's single-lock decision exists to prevent.

### Option 3 — Fully hermetic build (Nix, or apko/melange) — REJECTED for MVP
Steelmanned: apko and melange produce reproducible, digest-stable, minimal images with SBOMs and automated daily CVE rebuilds; Nix would give us `numeric_environment_hash` for free as a derivation hash and would make this entire record two paragraphs long. This is plausibly what a mature FarSight looks like and ADR-006 already conceded as much when it rejected the same option. Rejected here on the same grounds and one more: prebuilt Basilisk and SpiceyPy wheels are exactly what we do not want to rebuild, Windows development is where hermetic tooling is weakest, and the adoption cost lands in weeks 1-2 which are committed to the schema and hashing core. The numeric-environment hash is the majority of the benefit at a small fraction of the cost, and it is measurable in week 2.

### Option 4 — Accept ADR-006 literally: require a silicon-homogeneous runner fleet — REJECTED
Steelmanned, this is the simplest reading of the existing set, needs no code at all, buys certainty that dispatch pins cannot fail because there is nothing to dispatch over, and a fleet of identical self-hosted runners is an ordinary thing to purchase. Rejected on three grounds. It converts a software property into an unbudgeted procurement constraint inside an eight-week plan with three developers. It cannot be extended to customers, who build their own packages on their own machines, so Tier A would be a claim only we could make. And it is fragile in the least useful direction: a cloud runner fleet silently gains a new instance generation, and the first symptom is a red K3 with no diagnosis path.

### Option 5 — Build NumPy and SciPy from source with a fixed ISA target and `DYNAMIC_ARCH=0` OpenBLAS — REJECTED for MVP, retained as the pre-written replacement
This is the strongest technical alternative and it deserves to be said clearly: it **removes** runtime dispatch rather than suppressing it, gives complete control of compiler flags, and is what a national-laboratory reproducibility effort would actually do. Rejected because it puts a from-source scientific-stack build into weeks 1-2, and because it forks us off PyPI wheels, which means `uv.lock` no longer describes what is installed and ADR-014's single-lock property - the thing that makes the environment claim checkable at all - is lost. It also does nothing for Windows development. It is the named fallback if the dispatch pins prove ineffective, and the confidence row below is scored on that basis.

### Option 6 — Digest-pinned minimal base, uv-managed interpreter, dispatch pinned to a declared ISA baseline, `numeric_environment_hash` as the Tier-A predicate — CHOSEN
It pins what actually determines the bits, measures every field of the predicate from inside the process rather than trusting a declaration, turns a heterogeneous fleet from a silent hazard into a named refusal, and lets a rebuilt image satisfy Tier A without pretending image digests are reproducible.

## Consequences

**Buys us:** Tier A survives a mixed-silicon runner fleet and survives most base-image CVE rebuilds without touching a single golden. A machine that cannot support the claim is refused by name at job start instead of producing a mismatched hash hours later, which is the difference between K3 being diagnosable and K3 being the reproducibility kill. An auditor who cannot obtain our image can rebuild one and still get a Tier-A-valid environment. glibc, libm and the BLAS stop being version strings and become file hashes. And ADR-006's lowest-confidence row gets its named trigger discharged in advance rather than at the gate.

**Costs us:** the baseline forfeits AVX-512 on machines that have it, which is a real throughput loss on the 10k-run campaign that the plan budgets tightly. Two dispatch-control mechanisms whose exact spellings are version-dependent and currently unverified sit on the critical path of the hard gate. Hashing mapped shared objects costs time in a world where `max_tasks_per_child=1` means every run pays it; the mitigation is that the runner computes the numeric-environment document once per campaign in a probe process and passes the expected hash to workers, which then verify the *paths and sizes* they map - and the honest residue is that a mid-campaign library swap of identical size goes undetected. A named container owner and a monthly refresh job are standing overhead on a three-person team. And because the predicate covers the whole locked set present in the image, adding or removing an extra - descoping Basilisk under the plan's scope-cut order, for instance - moves the numeric environment and re-golds everything, which is a strong reason to settle the extras before the first goldens land in week 2.

**Forecloses:** Tier A on `aarch64` for the life of the MVP. Development on Apple Silicon is permanently a Tier-B activity, and a developer on that hardware cannot reproduce a golden locally at all - they can only compare tolerances. It forecloses claiming Tier A on any machine below `x86-64-v3`, so an older customer workstation is refused rather than silently downgraded, and that refusal is a sales conversation. It forecloses GPU or multi-threaded acceleration inside a Tier-A run just as firmly as ADR-006 did, and now for a second reason: the baseline pins are set before the numeric stack imports and cannot be relaxed per run. And it forecloses using the container image digest as the thing customers check, which is the intuitive artifact and the one a procurement questionnaire will ask about; we have to explain a hash they have never heard of instead.

## Enforcement

1. **CI job `ci-container-build`** (**first green by week 1**; every push touching `container/`, `pyproject.toml` or `uv.lock`). Fails if the `FROM` line carries no `@sha256:` digest; fails if any line in `packages.txt` lacks an exact `=version` pin; fails if the build emits an image whose recomputed `numeric_environment_hash` differs from `container/digests.json` without an `EXPECTED-CHANGE` note (ADR-006's re-golding discipline). On success it appends the built image digest to `accepted_image_digests`.
2. **`tests/unit/test_numeric_environment_hash.py`** (**first green by week 2**): asserts the document contains exactly the declared field list; asserts `container_image_digest`, `cpu_model_string`, hostname, PID and wall clock are **not** covered; asserts that mutating any covered field changes the hash; asserts every numeric value in the document is an exact-range integer and every physical or version quantity is a string, because the document is hashed and no hashed document may contain a JSON float (ADR-001); and asserts every digest-valued field matches `^[0-9a-f]{64}$`, so the `sha256:` prefix cannot re-enter through a formatter (ADR-001 decision 7).
3. **`tests/unit/test_isa_pins_readback.py`** (**first green by week 2**): runs inside the container, asserts `_ISA_ENV` is applied before the first numeric-stack import by checking import order in `worker.py` via AST, then asserts the feature set NumPy reports as enabled is exactly the declared baseline set and that no feature above baseline appears. A below-baseline machine must produce the environment-refusal exit code (defined in ADR-024) and must write no channel file.
4. **`ci-tier-a-bitwise`** (defined in ADR-006; **first green by week 3**) is the gate this record exists to make passable; it is not redefined here. This record contributes only the guarantee that its environment predicate is measurable and stable.
5. **PARTIALLY MECHANIZED: CI job `ci-isa-normalization`** (**first green by week 3**). Mechanical half: run the reference geometry plus link-chain run on every distinct runner shape the fleet offers and assert byte-identical output hashes; print `distinct_cpu_models_tested: N` in the job log. Residue, and it is the important half: if the fleet happens to be homogeneous, `N` is 1 and the job is green while having tested nothing - normalization is then *untested*, not *verified*, and a green tick would misrepresent that. Review checklist item **ENV-2** - "the Tier-A ISA normalization has been demonstrated on at least two distinct CPU models, or the shipped package states in writing that it has not" - carries it, and an ENV-2 row naming a reviewer and a date is recorded per release and copied into the `review_signoffs` list of every package built by that release (ADR-000, ADR-007).
6. **CI job `ci-container-refresh`** (monthly and on advisory; **first green by week 4**): rebuilds, recomputes `numeric_environment_hash`, appends the digest on no change, fails and files the re-golding task on change. CODEOWNERS on `container/` routes both outcomes to the named container owner.
7. **NOT MECHANIZABLE: ENV-3** - whether continuing to run a Tier-A image containing a known-CVE package for the remainder of an in-flight campaign is acceptable for a given deployment. No check decides that; it depends on the customer's site and on what the campaign is worth. Review checklist item **ENV-3** - "the decision to hold or move the numeric environment against an open advisory was taken deliberately, recorded with its reason, and is acceptable for every site this release ships to" - substitutes, and lands in `review_signoffs` for the release.
