# ADR-012 — Offline-first operation, structural no-telemetry, the signing seam, the audit log, and the logging mechanism
**Status:** Accepted 2026-08-28 (MVP commitment; see Revisit triggers)
**Date:** 2026-08-26
**Deciders:** FarSight founding engineering
**Plan reference:** FARSIGHT_FOUNDATION_PLAN.md §16 (Bake in now / Explicitly deferred), §12 (terminology note), §13 (package layout, `hashes/`), §15 (licensing conditions; export items 1 and 4), §20 Q2, §21 K7; decision D10 (SQLite for ledger, alias registry and audit log only)
**Related ADRs:** ADR-000 (the escape-hatch tokens this record's Enforcement uses), ADR-001 (the hash tree the signature seam attaches to), ADR-002 (workers are where temp files, tracebacks and crash dumps would otherwise leak customer data), ADR-006 (timestamps live only in the unhashed provenance block, which is why logs are not package content), ADR-007 (the package layout carrying `hashes/root_hash.txt`, the optional detached signature, and the `review_signoffs` rows this record's checklist items land in), ADR-011 (the `audit_log` table defined here shares the SQLite file with the run ledger), ADR-013 (import rules are the mechanism for the network and telemetry bans), ADR-014 (the dependency allowlist and `uv.lock` hash are the supply-chain half of the telemetry ban), ADR-024 (the CLI verbs `fetch` and `verify --audit` are spelled there), ADR-025 (the LLM-SDK exclusion is the same kind of structural absence as the telemetry one)

## Context

Four security properties are cheap in week 1 and effectively unbuyable later; everything else here is cheap later and expensive now. The forcing question is which four, and the discriminant is whether a property is *structural* — whether it constrains identity, the on-disk format, or the set of code paths that exist at all. A fifth item, the logging mechanism, joins them not because logging is a security property but because the worker-to-parent error payload is simultaneously the only post-mortem artifact we will have and the largest data-leak surface in the system, and it is forced in week 1-2 by the runner.

What breaks concretely. A customer's parameter values may themselves be EAR or ITAR technical data (§15 item 3); if a run's magnitudes reach a log line, a system temp directory or a crash dump, that is an export event on the customer's machine caused by our code, and no later release recalls the copies already written. If any release ever contains a network call in the runner or verifier, the procurement answer to "does this contain code capable of transmitting data" changes from "no such code path exists" to "there is a setting" — permanently, since deleting the code later only moves the honest answer to "not since 0.9". If the evidence identity scheme changes after customers hold packages, those packages become unverifiable by the current tool; §12 already forces the phrase "content-addressed, independently re-executable" over "cryptographically traceable" because signing does not exist yet, and that wording stays honest only while the hash tree it describes never moves.

A licensing consequence hides in the deployment choice: §15 records that mirroring the standalone SPICE toolkit requires written NAIF clearance, and an offline installer bundling standalone CSPICE walks into it. Nothing else about the offline posture requires shipping CSPICE ourselves, so the two are settled together.

## Decision

**1. Offline-first, structurally.** The runner and the verifier make zero network calls, ever. There is no offline mode and no online mode. Acquisition is a separate command on a separate code path:

```
farsight fetch kernel --url <url> --expect-sha256 <hex> --into <cache>
    -> writes bytes, records a DataArtifact:
       {url, sha256, size_bytes, fetched_at_utc, modified: false, license_note}
```

Everything downstream consumes content addresses, never URLs. `farsight.acquire` is the only package permitted to import an HTTP library, and the CLI's `fetch` subcommand is its only importer. `acquire/` is an addition to plan §6's source tree and carries a plan amendment request (see References). Kernels and referent data reach an air-gapped site as files the customer copies and the tool verifies against the recorded hash. We do not mirror the SPICE toolkit and we ship no installer containing standalone CSPICE: SPICE reaches the runtime through the SpiceyPy wheel, whose MIT wrapper bundles a compiled CSPICE and through which NAIF's terms flow. That wheel arrives only with the optional `spice` extra and never with a plain `pip install farsight`, which is what keeps the auditor's zero-extras install free of a compiled CSPICE (ADR-007, ADR-014; also a §6 amendment request). Kernels are redistributed only unmodified, and the manifest carries a `modified` flag because a modified kernel must be re-attributed to its modifier.

**2. The hash tree ships; the signer is a seam.**

```python
class SignatureBlock(Protocol):
    scheme: str               # "none" in MVP; "minisign-ed25519" later
    key_id: str | None
    signature: str | None     # base64, detached, over the root-hash bytes
    signed_at: str | None     # RFC 3339, provenance only, never hashed

class Signer(Protocol):
    def sign(self, root_hash: bytes) -> SignatureBlock: ...

class SignatureVerifier(Protocol):
    def verify(self, root_hash: bytes, block: SignatureBlock,
               trust_store: Path) -> SignatureOutcome: ...   # valid | invalid | absent
```

The MVP backend is `NoOpSigner`, returning `scheme: "none"`. The invariant that makes this a seam rather than a placeholder: **the signature covers the root hash and nothing about the signature enters the hash tree.** It lives at `hashes/root_hash.txt.minisig`, outside every hashed manifest field, so adding a real backend adds a file to a package whose identity does not change. `farsight evidence verify` reports `signature: absent (scheme=none)` and never the word "valid"; absence changes the exit code only under `--require-signature`.

**3. No telemetry, as an absence.** No phone-home code path exists — not disabled, not defaulted off, not behind a flag. No crash reporting, no update check, no license check-in, no usage counters. Enforced by the same socket-disabled suite and import rules as decision 1, plus a dependency allowlist so an analytics SDK cannot arrive transitively.

**4. Append-only hash-chained audit log, and strict data/config separation.** This record owns the table: its name, its columns and its chaining rule. ADR-011 owns the file it lives in and reproduces these columns without redefining them.

```sql
CREATE TABLE audit_log (
  seq         INTEGER PRIMARY KEY AUTOINCREMENT,
  ts_utc      TEXT NOT NULL,     -- RFC 3339; never enters an evidence hash
  actor       TEXT NOT NULL,     -- OS user only; no email, no installation id
  action      TEXT NOT NULL,     -- freeze | plan | run | resume | fetch | package
                                 -- | verify | replay | alias_set | collapse_authorize
  object_hash TEXT,              -- content address of the affected object, never its content
  detail_json TEXT NOT NULL,     -- validated: path-shaped and hash-shaped fields only
  prev_hash   TEXT NOT NULL,     -- 64 zeros for the genesis row
  row_hash    TEXT NOT NULL      -- sha256(JCS of the row minus row_hash)
);
```

Separation rules: configuration, object registry, ledger and audit log live under `$FARSIGHT_HOME`; mission data lives only under operator-declared `data_roots`, and a path outside them is refused rather than copied. Logs record paths, hashes and declared labels — never a parameter magnitude, never a channel value. Worker temp files live in a run-scoped directory under the output root and are removed on success; the system temp directory is never used (ADR-002). Traceback rendering that prints local variables is banned, so no dependency doing so may be added.

**5. Logging is structured JSONL to run-scoped files, the worker-to-parent error payload is a redacted traceback, and worker logs are not package content.** §16 item 4 gives the content rule and no mechanism; the runner forces the mechanism in week 1-2, so it is decided here.

*Library and format.* Stdlib `logging` is the API — no new dependency — with a single `JsonlFormatter` emitting one JSON object per line: `{ts_utc, level, event, run_index?, object_hash?, path?, label?}`. `event` is drawn from a closed enumeration; there are no free-text message strings and no `%`-style interpolation of caller data, because a closed event vocabulary with typed fields is the only version of the LOG-CONTENT rule that a validator can check at all.

*Destination.* The parent writes `$FARSIGHT_HOME/logs/<experiment_hash>/parent.jsonl`. Each worker writes `worker.jsonl` inside its own run-scoped directory under the output root (ADR-002). Nothing is written to the system temp directory. Standard output carries human-readable lines for the operator and is never an input to any hash.

*The worker-to-parent error payload.* ADR-002's "small result record" is made concrete: on a non-`ok` outcome it carries `{status, exc_type, traceback_text, worker_env_hash}`. A traceback string is the only useful post-mortem artifact, because there is no debugger on the parent and the worker is gone by the time the parent reads the record. It is also the largest leak surface in the system, so it is constrained rather than trusted: `traceback_text` is rendered by the standard library's traceback machinery in its default mode, explicitly and by name, never by a renderer that prints local variables — a rendered local *is* a parameter magnitude, and magnitudes are the thing §15 item 3 says we may not smear. Frame lines carry file paths and line numbers, which are path-shaped and permitted. The residual surface is the exception message itself: messages raised by FarSight code are constrained to the same path/hash/label vocabulary as log events, and messages raised by engine or third-party code are recorded to the worker's own `worker.jsonl` in full and truncated to exception type plus a bounded prefix in anything the parent writes or displays.

*Worker logs are deliberately not package content.* Every log line carries a wall-clock timestamp. ADR-006's determinism rule puts timestamps only in the unhashed provenance block, and ADR-007's byte-equal re-render rule would be unsatisfiable for any package containing them. So an auditor investigating a `diverged` run gets `status_<i>.json`, the `nonfinite_count` and `first_nonfinite_index` in `channels_manifest.json` (ADR-011), and the validity-violation register — and not our logs. We state this as a decision rather than leave it as an omission, and we carry the cost in Consequences: post-mortem of a customer's diverged run requires the customer to send us a file we deliberately did not ship inside the package.

**Explicitly deferred, each with why deferral is safe:** RBAC and authentication (single-operator CLI; the trust boundary is the OS user account, and adding auth later changes no hashed structure); encryption at rest (customer disk controls cover it, and it is transparent to the format); FIPS-validated modules (a build-and-procurement swap of the hash implementation); container tooling beyond a reference Dockerfile plus digest recording (the digest already sits in the environment fingerprint, which is the only thing later tooling must not break; ADR-019 owns what that Dockerfile is); PostgreSQL (decision D10 and §16: packages are files, and there is deliberately no DB roadmap line); any web UI. Every one is additive; none changes an identity, a file format, or a procurement answer irreversibly.

**Flagged legal dependency, not an engineering decision:** FarSight's own export classification once proprietary and non-published, which loses the EAR "published" carve-out and may fall under ECCN 9D515 after the 2024 space-controls rulemaking. Unsettled, and counsel's to answer (K7, by week 6). If it lands under 9D515, §15's sovereign-EU wedge is self-undermining and the deployment posture — who may download, from where, under what license — changes. Nothing here assumes an outcome.

## Options considered

### Option 1 — Defer all four structural properties to post-MVP — REJECTED
Three developers, eight weeks, and none of this is on the critical path to K3 or K6; security work shipped before a customer exists is a classic premature investment. Rejected because all four are retrofit-hostile: the network ban is a claim about every version ever shipped, the identity scheme freezes the moment a package leaves the building, the telemetry claim dies on one shipped counterexample, and leaked data cannot be recalled.

### Option 2 — Network-optional runner with an `--offline` flag — REJECTED
Substantially better ergonomics: kernels download on first use, referent data refreshes itself, week-1 setup becomes one command, and nearly every scientific Python tool works this way. Rejected because a code path that can reach the network can be reached — by a default, a dependency, a future contributor — so the claim degrades from a structural fact into an assertion about runtime behavior an auditor must take on trust. The flag also does not solve acquisition provenance: an auto-download still must record URL and hash, which is `farsight fetch`.

### Option 3 — Ship real signing in the MVP — REJECTED (two variants)
*Minisign now:* auditors ask for signatures, it is about a day of work, and a signature supplies the identity and timestamping that hashes alone cannot (§12). Rejected because §2's tripwire cuts any key-management document over one page, and a key we cannot yet rotate, escrow or protect is worse than no key — it invites reliance we cannot back. The seam makes it a one-day task in any later week, and §17 already places minisign fourth in the scope-cut order.
*Sigstore / keyless:* genuinely solves key management, and its transparency log supplies the independent timestamping a self-held key does not. The objection that it "requires the internet to verify" is false and we will not rest on it: a sigstore bundle carries the certificate chain and the inclusion proof, and offline bundle verification is a supported mode — which is precisely FarSight's requirement. The surviving objection is on the other side of the transaction: signing requires an OIDC identity and network access *at build time*, and the deployment model is that **customers build their own packages**, on their own machines, some of them air-gapped. A signing scheme that cannot run where the package is produced does not serve the packages that matter most. Rejected on that ground and no other.

### Option 4 — Opt-in anonymous telemetry, default off — REJECTED
Real value, honestly stated: crash rates, which engines and metrics get used, where campaigns stall. "Default off with a visible prompt" is defensible, and we are choosing to fly blind on product analytics for the life of the codebase. Rejected because procurement questionnaires ask whether the product contains any code capable of transmitting data, "off by default" answers yes, and the claim can never be re-earned once a release contains the code. This is the shakiest of the commitments in this record and its confidence row says so.

### Option 5 — Full security program now (RBAC, encryption at rest, FIPS, hardened container) — REJECTED
It would clear a whole class of procurement objections in one pass. Rejected on the discriminant: months of work, none of which changes an identity, a hash, or a file format — the definition of work that is safe to do later.

### Option 6 — A structured-logging dependency, or stdlib logging with free-text messages — REJECTED
Steelman both halves. A structured-logging library gives key-value discipline, context binding and rich exception rendering for free, and is what a normal Python service would use; free-text messages are how every engineer already writes logs, cost nothing to author, and are far more useful when someone is actually debugging. Rejected on two grounds. A new logging dependency in the base install is a procurement question we would have to answer forever ("what does it do at import time, and does it render locals?"), and a library whose exception renderer shows variable values would have to be *configured* out of that behaviour — converting a structural ban into a setting, which is the exact degradation Option 2 was rejected for. Free-text messages are rejected because they give LOG-CONTENT an unbounded surface: with arbitrary interpolation, no validator can bound what reaches a log line, and the only remaining enforcement is the reviewer's eye. A closed event enumeration with typed path/hash/label fields is checkable; a format string is not. The cost is real and we take it: our logs will be less pleasant to read than a normal service's.

### Option 7 — Worker logs ship inside the evidence package — REJECTED
This is the artifact an auditor most wants when a run diverges, and the difference between a package that says "run 8,300 diverged" and one that shows where. Logs are text, small, hashable, and shipping them would cost nothing structurally. Rejected on two grounds that both bite. Every line carries a wall-clock timestamp, so a package containing them can never satisfy ADR-007's byte-equal re-render rule or ADR-006's determinism rule; stripping the timestamps to fix that removes ordering and duration, which is most of the forensic value being bought. And worker logs are the one artifact in the system whose content rule is enforced by review rather than by schema, so shipping them to third parties would place the least-mechanized surface in the most-exposed position. The consequence — an auditor cannot post-mortem a diverged run from the package alone — is named in Consequences rather than hidden.

### Option 8 — The four structural commitments plus the logging mechanism, everything else deferred — CHOSEN
Days of work now for the properties that constrain identity, code-path existence and on-disk data placement; explicit deferral with a stated reason for everything additive.

## Consequences

**Buys us:** A procurement answer that is a fact rather than a setting on the three questions an aerospace buyer asks first. A stable evidence identity a signer can attach to without invalidating a single held package. An audit trail for every mutating CLI action from v0, which doubles as the debugging record for the campaign machinery. A log format whose content rule has a finite, checkable surface. And §15 item 4 stays closed, because we never mirror the standalone toolkit.

**Costs us:** Setup friction lands on the customer: kernels and referent data must be fetched deliberately, and first run is worse than with a tool that downloads what it needs. We will never have usage data, so prioritization runs on interviews and the engineer-hours ledger permanently. Any future dependency that touches the network at import time breaks CI loudly and must be replaced rather than configured. `data_roots` enforcement will reject legitimate paths and annoy operators in week 1. Our logs are event codes and typed fields rather than sentences, which is worse to read at 2 a.m. And because worker logs stay outside the package, diagnosing a customer's diverged run requires them to send us a file, which they may be unable to send at all if it sits inside an air-gapped facility — the deployment we are optimizing for is the one where our support story is weakest.

**Forecloses:** Every commercial model depending on phone-home — usage-based pricing, entitlement check-in, remote revocation, automatic updates — is off the table for the life of this codebase, because reintroducing the path retroactively falsifies the claim we sold on. Crash reporting goes with it, so field failures reach us only as customer-mailed files, if at all. Until a signing backend lands we cannot claim non-repudiation or trusted timestamping, and auditors who require signed artifacts are unserved. The audit log is tamper-*evident*, not tamper-*proof*: an operator with write access can recompute the whole chain, so it will never support an insider-threat claim without external anchoring, which is deferred with the signing story.

## Enforcement

- **PARTIALLY MECHANIZED: CI job `test-no-sockets`** (**first green by week 1**). Mechanical half: the whole suite runs with sockets disabled (`pytest-socket`, unix sockets included, plus an autouse fixture raising from `socket.socket` and `socket.create_connection`); any Python-level network attempt fails and names the caller. This is *not* a proof that no network access occurs. `pytest-socket` patches Python's socket module inside the test process; it does not see a subprocess that opens its own socket, a compiled extension or C library calling out beneath Python (CSPICE, a BLAS, an engine SDK), or a `ctypes` call. Two mechanisms narrow the residue rather than paper over it: the import-linter contract below is sound for imports, and the Linux container leg of CI runs the suite in an isolated network namespace with no route out, which does catch subprocess and C-library traffic. The Windows leg has no equivalent and is the honest remaining gap. Review checklist item **NET-1** — "no new subprocess, compiled dependency or `ctypes` call in this change can reach the network on Windows" — carries it, and a NET-1 row is recorded per release and copied into the `review_signoffs` list of every package built by that release (ADR-007).
- **import-linter contract `no-network-in-truth-loop`** (**first green by week 1**): `socket`, `http`, `urllib`, `ftplib`, `smtplib`, `requests` and `httpx` are forbidden in every `farsight` package except `farsight.acquire`, which is itself importable only from the CLI's `fetch` module. Sound within its scope: imports are decidable, and this is a statement about imports.
- **Dependency allowlist check** (ADR-014 owns it: `tests/unit/test_dependency_allowlist.py`, run inside CI job `env-guard`; **first green by week 1**): the top-level distribution names in `uv.lock` must equal the literal list checked into that test; analytics and error-reporting SDKs sit on a permanent denylist inside it. This record does not maintain a rival list and does not diff a Markdown table.
- **`tests/unit/test_signature_seam.py`** (**first green by week 4**, with the first package builder): adding, removing or corrupting `hashes/root_hash.txt.minisig` must leave the root hash unchanged; `verify` with a no-op block must report `absent` and never `valid`; a tampered channel must fail hash verification before any signature check runs.
- **`tests/unit/test_audit_chain.py`** plus `farsight verify --audit` (**first green by week 2**): mutating or deleting any row fails chain verification naming the `seq`; a schema validator rejects any `detail_json` field that is not path-shaped, hash-shaped or an enumerated label. The audit check is folded into plan §6's existing `verify` verb as a flag rather than introduced as a new `farsight audit` command; ADR-024 owns the CLI surface.
- **`tests/unit/test_log_schema.py`** (**first green by week 2**): every log record emitted anywhere in the suite must validate against the JSONL event schema — `event` in the closed enumeration, every other field path-shaped, hash-shaped or an enumerated label. A log call with a free-text message or an undeclared field fails the test. This is the mechanizable majority of LOG-CONTENT, and it exists because the closed vocabulary was chosen to make it possible.
- **`tests/unit/test_traceback_redaction.py`** (**first green by week 2**): raises an exception inside a worker whose frame locals contain a canary magnitude, asserts the returned `traceback_text` contains file paths, line numbers and the exception type and does **not** contain the canary; asserts the renderer in use is the standard library's default and that no locals-rendering renderer is importable from the base install.
- **PARTIALLY MECHANIZED: `tests/integration/test_data_leak_canary.py`** (**first green by week 2**): a scenario runs with a unique canary token as a parameter label and magnitude; the token must appear in no log file, no file under the system temp directory, and no file outside the declared output root. Stated limit: this is a sampling check over enumerable paths for the tokens it is given, not a proof of non-leakage — it cannot see a token that was transformed, truncated or encoded, and it cannot enumerate paths a dependency chose. Covered by NET-1 and LOG-CONTENT for the residue.
- **NOT MECHANIZABLE:** whether a log message or exception string is semantically revealing about a customer's system. No parser decides that, and prose analysis of a message would be a check we could not defend. Review checklist item **LOG-CONTENT** — "every new log event and exception string interpolates only paths, hashes and enumerated labels, and reveals nothing about the customer's system that those three do not already reveal" — substitutes. `test_log_schema` mechanizes the syntactic half, the canary test samples the runtime half, and a LOG-CONTENT row naming a reviewer and a date is recorded per release and copied into the `review_signoffs` list of every package built by that release (ADR-007). This record makes no claim to be free of reviewer judgement: two of its checks end in a human, and both say so by name.
