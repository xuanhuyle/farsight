# ADR-016 — Kernel sets: identity, furnish order, metakernels, coverage and the kernel cache
**Status:** Accepted 2026-08-28 (MVP commitment; see Revisit triggers)
**Date:** 2026-08-26
**Deciders:** FarSight founding engineering
**Plan reference:** FARSIGHT_FOUNDATION_PLAN.md §17 (weeks 1-2: content-addressed kernel cache, Psyche and station kernels from NAIF PDS4), §5 (SPICE ground truth: global kernel pool, per-worker furnishing), §13 (`inputs/kernels.manifest.json`), §15 (NAIF kernel redistribution; modified kernels re-attributed to the modifier), §16 item 1 (`farsight fetch` records URL and hash), §6 (`registry/` holds the kernel cache); decision D3 (refusal is a first-class outcome)
**Related ADRs:** ADR-015 (the LSK pinned here authorizes every time conversion, and the PCK and FK pinned here realize every frame that record names), ADR-003 (defines `furnish(kernels: Sequence[KernelRef])` and leaves `KernelRef` and the significance of order to this record), ADR-001 (a `KernelSet` is a frozen content-addressed object and its hash is a hashed run input), ADR-011 (decides exactly three stores and names the kernel cache as this record's fourth), ADR-012 (`farsight fetch` and the `acquire/` package are the only writers of the cache, and the only permitted HTTP path), ADR-007 (`inputs/kernels.manifest.json` and the `self_contained` closure that embeds kernel bytes), ADR-002 (kernels are furnished per worker, and SPICE is the one adapter granted `reusable_worker`), ADR-005 (the planner is pure, which is why coverage is attested at freeze rather than read at plan time), ADR-023 (the outcome a coverage failure at run time resolves into), ADR-006 (Tier-A geometry claims are claims about a fixed kernel sequence), ADR-024 (the CLI verbs the fetch and attest steps are spelled in), ADR-000 (the escape-hatch tokens and the `review_signoffs` field KERN-1 and KERN-2 land in)

## Context

The forcing question is the week 1-2 deliverable stated in one line: **what exactly is the kernel input of a run, such that two machines that agree on a `spec_hash` cannot disagree about the geometry it produces?**

Three verified properties of SPICE make that harder than it looks. The kernel pool is global, mutable and not thread-safe, so kernels are furnished per worker process (plan §5, ADR-002). Furnishing is *ordered*: a later kernel overrides an earlier one for the same pool assignment, so the sequence carries meaning that a set does not. And a metakernel — NAIF's own packaging unit, the thing every SPICE user already has — is a text file whose `PATH_VALUES` are absolute paths on the machine that wrote it.

Each of those turns into a specific defect if left undecided. If the hashed run input is a kernel *set* rather than an ordered sequence, two runs carrying the identical `spec_hash` can legitimately produce different numbers, because the two orderings resolve a pool collision differently. That is the single worst failure mode this product can have: a non-reproducible result whose hash asserts reproducibility. It would surface as K3 (end wk 3, hard gate) going red intermittently and undiagnosably, and every diagnostic instinct would point at FarSight's arithmetic rather than at an ordering. If the metakernel's text is what we hash, the package identity contains a machine's directory layout and no auditor can verify it anywhere else — while if it is excluded without saying so, the kernel set becomes an ambient property of whoever ran the job. And if the epoch coverage of an SPK is never checked until CSPICE raises, the refusal principle ADR-003 built the whole adapter contract around — refuse at freeze, do not fail at run 8,300 of an overnight campaign — is absent from the one input most likely to be short.

Two further things are unowned and land here because nothing else can hold them. The kernel cache is a **fourth store**: ADR-011 decides exactly three (object, channel, ledger) and explicitly names this record as the owner of the fourth. And the LSK and PCK selection is the input to ADR-015's leap-second and Earth-orientation decisions — that record's conversions are authorized by "the LSK", which only means something once exactly one LSK is guaranteed to be in the pool.

## Decision

**1. A `KernelRef` is a content address plus the metadata that redistribution and validation need.**

```python
class KernelRef(BaseModel, frozen=True, extra="forbid"):
    sha256: str            # 64 lowercase hex over the kernel file bytes; the only identity
    kernel_type: Literal["spk", "pck", "ck", "sclk", "lsk", "ik", "fk", "dsk", "ek"]
    logical_name: str      # the publisher's own file name, for humans; never a lookup key
    size_bytes: int        # exact-range integer (ADR-001 rule 2 permits counts)
    attribution: Literal["naif_unmodified", "third_party_unmodified",
                         "farsight_authored", "modified"]
    modifier: str | None       # required unless attribution is *_unmodified
    parent_sha256: str | None  # required when attribution == "modified"
    license_note: str
```

`kernel_type` deliberately has no `mk` member: a metakernel is an import format, never a run input (decision 3). `logical_name` is provenance and display only; nothing resolves a kernel by name, which is what stops a file called `earth_latest_high_prec.bpc` from being a moving target inside a frozen document.

**2. The hashed run input is an ordered `KernelSet`, and reordering is an identity change.**

```python
class KernelSet(BaseModel, frozen=True, extra="forbid"):
    kernels: tuple[KernelRef, ...]                    # FURNISH ORDER; later overrides earlier
    frame_sources: Mapping[str, tuple[str, ...]]      # frame name -> the sha256s that realize it
```

`kernel_set_hash = sha256(JCS(object))` under ADR-001, and the `RunSpec` carries the hash as an input. A different order is a different object even when the multiset of kernels is identical. Validators reject a duplicate `sha256` inside one sequence, because a repeat is always either a mistake or a no-op, and reject a sequence containing zero or more than one `lsk` — exactly one leap-second kernel, so that ADR-015's phrase "the LSK" denotes something.

`frame_sources` is the semantic half of the same defence. Which kernel actually realizes `ITRF93` in a furnished pool is otherwise an emergent property of ordering that nobody reads; here it is a declaration checked at freeze (Enforcement item 4). The value is a tuple rather than a single hash because a frame is routinely defined by one kernel and driven by another — a frames kernel plus the binary orientation PCK that supplies its data.

The worker furnishes exactly this sequence, in exactly this order, and proves it did:

```python
def furnish_in_order(seq: Sequence[KernelRef], cache: Path) -> None:
    for ref in seq:                                   # the order IS the decision
        path = cache / ref.sha256[:2] / ref.sha256
        verify_sha256_once_per_process(path, ref.sha256)
        spiceypy.furnsh(str(path))                    # one file at a time; never a metakernel
    if spiceypy.ktotal("ALL") != len(seq):            # a silently-skipped furnish is a defect
        raise UnhonorableSpec(...)                    # ADR-003
```

**3. Metakernels are an import format and never a runtime artifact.** The runtime furnishes files individually, which is exactly equivalent to a metakernel's effect and removes the absolute-path problem instead of managing it. A customer-supplied metakernel is *expanded* at import into an ordered `KernelSet`; the metakernel's own bytes are recorded as a `DataArtifact` for provenance, with its expansion, and that artifact is never a run input and never consulted at replay. No metakernel is generated per worker, so there is no per-machine text to exclude from a hash and no question about whether the exclusion was honoured.

This is a departure from plan §13, which puts "metakernel text" inside `inputs/kernels.manifest.json`. Under this record that file carries the ordered `KernelSet`, the per-kernel hash, size, source URL and attribution, and the coverage attestation of decision 4; the source metakernel appears only as an optional provenance artifact, explicitly marked as not a run input. The amendment is requested in References.

**4. Coverage is attested at freeze, and a run whose epochs fall outside coverage fails there.** The attestation is a hashed object, produced by the code path that furnishes kernels and therefore permitted to read them:

```python
class CoverageWindow(BaseModel, frozen=True, extra="forbid"):
    kernel_sha256: str
    object_id: str        # NAIF integer id as a string, or a frame name
    start: Epoch          # ADR-015
    stop: Epoch

class CoverageAttestation(BaseModel, frozen=True, extra="forbid"):
    kernel_set_hash: str
    windows: tuple[CoverageWindow, ...]
    produced_by: str      # tool version + CSPICE and SpiceyPy versions; no timestamp (ADR-001 rule 4)
```

This is how a **pure planner reads kernel coverage without doing I/O**: it does not. The attestation is produced once, before freeze, by `farsight/engines/spice/` under the `spice` extra; `freeze` runs the validator `kernel_coverage_completeness`, which intersects the design's requested epoch span and the bodies and frames its `GeometryRequest`s name against the attested windows, and refuses — naming the kernel, the object and the gap — if any requested epoch is uncovered. The planner then consumes the attestation as ordinary hashed data. The consequence is stated plainly rather than buried: **freezing a design that declares a `KernelSet` requires the `spice` extra; verifying a package never does.** Authoring and auditing are different acts with different installs, and the auditor boundary (import-linter contract `auditor_boundary`, defined in ADR-013) is untouched, because the attestation crosses it as JSON.

If a coverage error nonetheless reaches CSPICE at run time, it is a `failed` run, not `diverged` — the taxonomy is ADR-023's — and it is treated as a defect in the attestation rather than as a physical result.

**5. The kernel cache is the fourth store: content-addressed, immutable, and written by exactly one code path.** Kernels live at `$FARSIGHT_HOME/kernels/<first2>/<sha256>` with no extension and no logical name in the path, so nothing can resolve a kernel by anything but its content. The store holds bytes; the `DataArtifact` record describing a kernel is a JSON object in the object store (ADR-011) that points at it. Only `farsight.acquire`, via `farsight fetch` (ADR-012), writes to the cache; every other package treats it as read-only. There is no automatic eviction, no garbage collection and no `prune` command in the MVP: a cache that can delete a kernel a shipped package references is a way to make a package unverifiable by accident.

Integrity is verified on insert, on package build, and on furnish. Because verifying a large SPK on every furnish is the one place this rule could get expensive, the worker memoizes verified `(path, sha256)` pairs **per process**, so a recycled SPICE worker (ADR-002's single `reusable_worker` grant) re-furnishes per run but re-hashes once per process. The residue is named rather than hidden: another process could modify a cache file mid-campaign, and nothing catches that until the next process starts. Enforcement item 7 measures the verification cost in week 1 so this is a decision with a number attached rather than an assumption.

**6. LSK and PCK selection, as the input to ADR-015.** Exactly one `lsk` per `KernelSet` (decision 2), which is what makes "the pinned LSK" in ADR-015's conversion records denote a single kernel. Earth orientation enters only through a binary orientation PCK that realizes `ITRF93`, declared in `frame_sources["ITRF93"]`; that kernel's coverage is attested like any other, and a design whose epochs fall outside it fails at freeze rather than silently falling back to a low-precision rotation model. Which archived high-precision Earth PCK covers the DSOC benchmark span is **UNVERIFIED — confirm at implementation time**, and it is the first thing `kernel_coverage_completeness` will tell us in week 1.

**7. NAIF attribution is a schema field, not a norm.** Plan §15 permits free redistribution of unmodified kernels and requires modified kernels to be re-attributed to the modifier. `attribution` carries that: `naif_unmodified` may be stamped only when the bytes hash equals the hash `farsight fetch` recorded at acquisition from the publisher's URL; `modified` and `farsight_authored` require a `modifier`, and `modified` additionally requires `parent_sha256`, so a derived kernel always names what it was derived from. FarSight never edits a kernel in place — a modification is a new content address with a recorded parent — and `NOTICES.md` in the evidence package (ADR-007) is generated from these fields, which is what makes the `self_contained` closure's embedded kernel bytes lawful to redistribute.

## Options considered

### Option 1 — Hash the ordered sequence, with declared frame sources — CHOSEN
The hashed input is exactly what determines the geometry: the same files in the same order. It costs one tuple instead of one set and it makes the pool-override hazard an identity difference rather than a mystery.

### Option 2 — Hash the kernel *set*, canonically sorted by hash — REJECTED
This is what a content-addressing instinct reaches for, and the argument is good: order-independence is the whole point of a canonical form, a sort makes two authors who listed the same kernels agree on one identity, and it removes a class of spurious hash differences that will otherwise cause duplicate campaigns at full compute cost. Rejected because SPICE's pool semantics make order *semantically significant* — a later kernel overrides an earlier assignment — so canonicalizing the order does not remove noise, it destroys information the numbers depend on. Two runs sharing a `spec_hash` could then produce different geometry, which inverts the meaning of every hash in the product. The dedup cost is real and is carried in Consequences.

### Option 3 — The metakernel text is the hashed identity — REJECTED
Stated at its strongest, this is not a shortcut: the metakernel is NAIF's own packaging unit, it is what mission operations groups already maintain and hand to each other, it captures order natively, it is a single small text file to ship inside a package, and hashing it is a one-liner. Adopting it would make FarSight's kernel identity the same object the customer already curates. Rejected because the text embeds `PATH_VALUES` and `PATH_SYMBOLS` that are absolute paths on the machine that authored it, so the hash is partly a hash of a directory layout; a package would verify only where it was built, which contradicts the one property the package exists to have. Metakernels may also reference files by paths resolved relative to the process's working directory, which makes identity depend on where the process was launched. It survives as an import format, which is the role it can hold honestly.

### Option 4 — Kernels as an ambient environment dependency — REJECTED
Point the tool at a kernel directory, or set an environment variable, and let SPICE find what it needs. This is how essentially every SPICE-using codebase works, it is what NAIF's own examples do, it costs no schema and no cache, and it would delete a week-1 deliverable outright. Rejected because it makes geometry a property of the machine rather than of the spec, which is precisely the silent-killer class plan §14 item 3 names, and because a run whose inputs are ambient cannot be replayed from package content only (AT-1). Every other decision in this set assumes the causal inputs of a run are inside its hash; kernels are the largest of those inputs.

### Option 5 — Check coverage lazily, at run time, and let CSPICE raise — REJECTED
The steelman is not laziness. CSPICE already produces a precise, specific error naming the body and the epoch; no freeze-time machinery is needed; the planner stays pure trivially; and a coverage check performed at freeze can be *stale* relative to the kernels a worker actually furnishes, so early checking checks something that could still change. Rejected because the timing is the point: refusal at freeze rather than failure at run 8,300 of an overnight campaign is ADR-003's organizing principle, and the overnight campaign is the exact scenario the plan budgets for. The staleness objection is answered structurally — the attestation names `kernel_set_hash` and every kernel `sha256`, and the worker verifies those same hashes before furnishing, so an attestation can be wrong about a window but cannot be about a different kernel.

### Option 6 — Fold the kernel cache into the object store as another content-addressed blob — REJECTED
The plan itself puts kernels in the knowledge plane as `DataArtifact`s alongside referent files, both SHA-256 addressed (§4), so one store keyed one way is the coherent reading and it would give cross-workspace dedup for free. Rejected because the object store holds canonical JSON documents at `objects/<first2>/<hash>.json` (ADR-011) and is walked in full by `verify`, by package build and by dedup; putting multi-hundred-megabyte binaries in that walk makes every one of those operations proportional to kernel volume. The compromise keeps both properties: the `DataArtifact` *record* is an object in the object store, and the *bytes* are in a separate cache keyed identically, so sharing survives and the walk does not.

### Option 7 — Ship a curated FarSight kernel bundle — REJECTED
It would remove the entire acquisition step from onboarding, guarantee a known-good set for the benchmarks, and make the week-1 exit gate a one-command affair. Rejected on licensing and on posture: plan §15 records that mirroring the standalone SPICE toolkit requires written NAIF clearance, and while kernels themselves redistribute freely when unmodified, becoming a kernel distributor means owning currency, correction notices and re-attribution for files we did not produce. ADR-012 already decided that acquisition is an explicit, hash-recording `fetch` on a separate code path; a bundle would be a second, implicit one.

## Consequences

**Buys us:** a kernel input that is fully inside the run's hash, ordering included, so a geometry difference between two runs is always a difference in their specs; a mechanical proof that the ordering decision is load-bearing rather than defensive (Enforcement item 2); refusal at freeze for the input most likely to be short, in the form the rest of the adapter contract already speaks; an auditor who can verify a package on a machine that has never seen a metakernel; and a redistribution story where attribution is a required field rather than a paragraph someone remembers.

**Costs us:** a fourth store to back up, explain and never garbage-collect, whose size is dominated by files we did not write. An expansion step on every customer onboarding, because their kernel set arrives as a metakernel and ours is an ordered list. Hash verification on every furnish, whose cost is a week-1 measurement rather than a known quantity. And a freeze path that needs the `spice` extra, which splits the install story in two and means an analyst on a bare install can author a design but not freeze it.

**Forecloses:** semantic deduplication of kernel sets. Two customers who list the same kernels in two equally valid orders get different `kernel_set_hash`es, therefore different `spec_hash`es, therefore duplicate campaigns at full compute cost — the same syntactic-identity cost ADR-001 pays for significant figures, paid a second time here, and nothing in the system will point it out.

It forecloses "point FarSight at my kernel directory" permanently. That is the single most requested workflow in this domain and we will be saying no to it in sales conversations: every kernel must be fetched or imported by hash first, and a metakernel is only ever an input to that step.

It forecloses automatic kernel currency. A mission that publishes an improved reconstructed SPK does not improve any existing FarSight result: every published number is pinned to a kernel vintage, and moving to a new vintage is a new `KernelSet`, a new `experiment_hash` and a new campaign, never a refresh. Comparing across vintages is therefore a deliberate cross-campaign exercise with its own claim statement — which is honest, and which also means we can never quietly ship a better answer to a question a customer already has an answer to.

And it forecloses a warm kernel pool as a performance strategy. Kernels are re-furnished per run even in the one recycled worker, so a campaign whose dominant cost is furnishing a large SPK pays that cost per run; the only lever left is `reusable_worker`'s per-process hash memo, and ADR-002's own confidence row already treats that exemption as provisional.

## Enforcement

1. **`test_kernel_sequence_identity`** (unit tier, every commit, Windows and Linux; **first green by week 1**): reordering the `kernels` tuple changes `kernel_set_hash`; a duplicate `sha256` in one sequence is rejected at construction; a sequence with zero or two `lsk` entries is rejected naming the count; `attribution == "modified"` without `modifier` and `parent_sha256` is rejected; `logical_name` never appears in any path the cache resolver builds.
2. **`ci-kernel-override-canary`** (defined here; container leg, needs the `spice` extra; **first green by week 2**): a deliberately constructed two-kernel case in which the later kernel overrides an assignment made by the earlier one — both text kernels authored by FarSight, attributed `farsight_authored`, hash-pinned in the fixture manifest. The job asserts that the two orderings produce **different geometry** and **different `kernel_set_hash`es**. This is the direct mechanical proof that decision 2 is load-bearing; if the first assertion cannot be made to hold, the first row of the Confidence table fires.
3. **Freeze validator `kernel_coverage_completeness`** (**first green by week 2**, which is what the weeks 1-2 exit gate dates it to): a design whose requested epoch span, bodies or frames are not covered by the `CoverageAttestation` fails at freeze, exits nonzero, and names the kernel `sha256`, the object and the uncovered interval. A design declaring a `KernelSet` with no attestation, or an attestation whose `kernel_set_hash` does not match, fails the same way.
4. **`test_frame_source_is_last_writer`** (container leg, needs the `spice` extra; **first green by week 2**): furnishes the sequence one kernel at a time and, after each, computes the transformation from each declared frame to `J2000` at a sample epoch; the last index at which that transformation changes must belong to the tuple declared in `frame_sources` for that frame. This is the mechanical detection of the pool-override hazard at the level that matters — which kernel actually decided the frame — rather than at the level of file order.
5. **`test_no_metakernel_at_runtime`** (unit tier plus AST lint; **first green by week 1**): `furnsh` is called from exactly one helper module; a lint fails on any `.tm` path literal or `KERNELS_TO_LOAD` or `PATH_VALUES` string anywhere under `src/farsight/` outside the importer that expands metakernels; the helper asserts the loaded-kernel count equals the sequence length after furnishing and raises `UnhonorableSpec` (ADR-003) otherwise.
6. **`test_kernel_cache_integrity`** (unit tier; **first green by week 1**): a cache file whose bytes do not hash to its own path name is rejected on read, naming the path; the per-process verification memo is asserted to be keyed on `(path, sha256)` and to be process-local; and an AST lint fails on any write to the cache root outside `farsight.acquire` and the cache module, which is the local half of ADR-012's rule that `acquire/` is the only code path that fetches.
7. **`bench_kernel_verify`** (a measurement task rather than a pass/fail gate; **first green by week 1**, meaning it runs and reports by then): records SHA-256 verification wall time for the Psyche SPK, the station SPKs and the binary Earth PCK on the reference workstation, together with a geometry run's total wall time, and the ratio is written back into this record's Confidence table. A measurement with no scheduled date is an intention, so it has one.
8. **PARTIALLY MECHANIZED: KERN-1** — the zero-extras verifier cannot recompute a coverage attestation. `farsight evidence verify` (defined in ADR-007; **first green by week 4**) checks mechanically that the attestation resolves to the declared `kernel_set_hash`, that every `kernel_sha256` it names is present in the manifest and matches the embedded or referenced bytes, and that every requested epoch lies inside an attested window. What it cannot do without the `spice` extra is check that the windows are *true* — that they are what the kernels actually contain, correctly composed across the frame and body chain the design requests. Residue: an attestation that is internally consistent and wrong, because the composition logic is ours. Review-checklist item **KERN-1** — *"the coverage attestation was produced by the same furnish path the run uses, and its window composition was reviewed against the frame and body chain this design actually requests"* — substitutes and lands in `review_signoffs` on the frozen `ExperimentDesign` (ADR-000). The mechanized half is **first green by week 2** at freeze and **week 4** inside `verify`.
9. **PARTIALLY MECHANIZED: KERN-2** — whether a kernel marked `naif_unmodified` really is NAIF's unmodified publication. `test_kernel_attribution` (**first green by week 2**) mechanizes what is decidable: `naif_unmodified` may be stamped only when the stored bytes hash equals the hash `farsight fetch` recorded at acquisition, the `DataArtifact` carries the source URL, no FarSight code path opens a cache file for writing, and `NOTICES.md` generated for a package names every non-`*_unmodified` kernel with its modifier. What no check can establish is that the URL was a publisher's, or that a customer-supplied file is unmodified relative to a publication we never saw. Residue: provenance upstream of our first sight of the bytes. Review-checklist item **KERN-2** — *"every kernel marked `naif_unmodified` was obtained from a publisher URL recorded in its `DataArtifact`, and no kernel in this set was edited by us or by the customer without being re-attributed"* — substitutes, landing in `review_signoffs` on every `EvidencePackage` whose kernel manifest is non-empty (ADR-007).
10. **`ci-tier-a-bitwise`** (defined in ADR-006; **first green by week 3**) is the standing integration guard for this record: a geometry result is a Tier-A claim about a fixed kernel sequence, so any drift in furnish order, cache contents or verification behaviour surfaces there as a hash difference at gate K3. This record adds no second job for it. `ci-geometry-crosscheck` (defined in ADR-015; **first green by week 2**) is where a wrong-but-stable kernel choice is caught instead, against Horizons and astropy.

- **PLAN AMENDMENT REQUESTED: §6** — extras become `spice`, `basilisk`, `gmat`, `analysis`, `dev`. `spiceypy` is an optional extra named `spice` and never a core dependency, so the auditor's zero-extras install cannot pull a compiled CSPICE; §6 lists extras as `basilisk, gmat, analysis, dev`. This record depends on the change because decision 4 states which side of that line freeze sits on and which side verification sits on. ADR-014 owns the dependency table.
- **PLAN AMENDMENT REQUESTED: §6** — `acquire/` is added to the source tree as the `farsight fetch` code path and the only package permitted an HTTP import. §6's tree does not list it, and decision 5's single-writer rule for the kernel cache is written in terms of it. ADR-012 owns the package and requests the same amendment; it is repeated here because this record's Enforcement item 6 lints against it by name.
- Refinement of §6, not a departure: §6 already places the kernel cache under `registry/`. This record fixes its layout as `$FARSIGHT_HOME/kernels/<first2>/<sha256>` and names it the fourth store that ADR-011's "three stores" deliberately excludes.
- Refinement of §15, not a departure: the plan states the re-attribution rule in prose. This record makes it the `attribution`, `modifier` and `parent_sha256` fields of a hashed object, so that an unattributed modified kernel is a validation error rather than a review finding.
