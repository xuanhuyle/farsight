## Results

| | Question | Result |
|---|---|---|
| Q1 | Does a propagation complete in a fresh subprocess? | yes |
| Q2 | Same inputs, two separate processes → identical? | **bit-identical** |
| Q3 | Different inputs → different output? | differs (Q2 is not vacuous) |

Physics sanity check: at SMA 7000 km the propagated state gives |r| ≈ 6994 km and |v| ≈ 7.55
km/s against the circular expectation √(398600/7000) = 7.546 km/s. The round-trip is returning
real numbers, not a stub.

## ADR-014's UNVERIFIED items, now verified

**The API entry point is `api/load_gmat.py`** — as ADR-014 recorded, but with a detail that
matters to the adapter: *it ships as a template containing the literal placeholder
`<TopLevelGMATFolder>` and does not run until a human edits it.* An adapter cannot depend on a
file the user has hand-edited, so the adapter must replicate its logic instead — insert
`<root>/bin` on `sys.path`, `chdir` there, `import gmatpy`, and call `gmat.Setup(startup)`.

**A GMAT install is not API-ready as shipped.** `bin/api_startup_file.txt` does not exist in the
distribution; it is generated by `python api/BuildApiStartupFile.py`, which rewrites the relative
paths in `gmat_startup_file.txt` to absolute ones. The adapter must either run that or check for
its output and refuse with a message naming it. This is exactly the kind of environment
precondition that becomes an hour of confusion in week 5 if it is discovered then.

**Python 3.12 is supported, and 3.13 is not.** `bin/gmatpy/` ships prebuilt bindings for
`_py36` through `_py312` inclusive. ADR-014 pinned 3.12 as "the ceiling of the GMAT and Basilisk
intersection" from documentation; that is now confirmed against the shipped artifact, and the
absence of `_py313` confirms the ceiling is real rather than conservative.

## The correction: ADR-002's justification is partly wrong

ADR-002 mandates one fresh OS process per run, and justifies it in part with GMAT having "no
reliable reset". Half of that is confirmed and half is not.

**Confirmed:** a naive second setup in the same process fails, loudly —

> `APIException: ODEModel Exception Thrown: Attempted to add a GravityField force to the force
> model for the body Earth, but there is already a GravityField force in place for that body.`

State from the first run persists in the engine's object store. Anyone who assumed they could
loop over cases in one process finds out immediately, which is the good version of this failure.

**Not confirmed:** `gmat.Clear()` *did* reset the engine, the second run completed, and its
result was **bit-identical** to the same case run in a virgin process. On this evidence the
reset works. One simple point-mass case is not proof that it works in general — the community
pattern is subprocess-per-run for reasons that presumably include cases where it does not — but
this spike found no instance of unreliability, and the ADR should not claim evidence it does not
have.

**The decision does not change; its reasoning should.** Process isolation remains correct on
grounds this spike positively supports: it is required for CSPICE's global kernel pool
regardless (ADR-016), it gives crash containment, and it makes the environment fingerprint
uniform across every engine (ADR-002, ADR-019). Those arguments stand on their own. The "no
reliable reset" clause should be softened to something like *"reset via `gmat.Clear()` appears
to work for simple configurations; process isolation is chosen for crash containment and uniform
fingerprinting, and does not depend on reset being impossible."*

Recommended follow-up: amend ADR-002's References with this finding rather than editing its
Decision, since the decision is unchanged. Under ADR-000 an accepted record's Decision may not be
edited in place, and nothing here warrants a superseding record.

## What this does not establish

- **Windows only, one trivial case.** Two-body point-mass, ten 60-second steps. Nothing exercises
  the force models, event location, or estimation surfaces a real cross-validation would use.
- **Nothing about cross-engine agreement.** Q2 is GMAT agreeing with *itself*. ADR-006's Tier C —
  GMAT against Basilisk under a matched configuration — is untouched, and is where the real
  difficulty lives (plan §19 risk 1 ranks matched-configuration work as the likeliest three-week
  sink in the project).
- **No adapter.** This is the API responding, not FarSight driving it through `StageSpec` and
  `config_ref`.
- **Disk cost is real.** ~409 MiB compressed, ~1.5 GB extracted, and it is a user-installed tree
  rather than a dependency — which is precisely why ADR-014 keeps GMAT out of `pyproject.toml`
  and records it in the registry as an `EngineBuild` with a path and a content hash. That
  decision looks better after handling the artifact than before.

## Recommendation

Keep GMAT post-MVP and keep the subprocess-per-run execution model. Carry three concrete facts
into the adapter when it is written in Stage 3: the startup file must be generated before first
use, `load_gmat.py` is a template to be replicated rather than imported, and `Clear()` is a
usable reset that the design nonetheless does not rely on.
